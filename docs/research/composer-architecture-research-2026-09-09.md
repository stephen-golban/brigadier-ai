## Intended architecture

**Brigadier's durable conversation is owned by Rust, independently of model context.** The harness owns goal, plan, progress, remaining work, diffs, and displayed thread. It rents bounded model windows for decisions and work, then discards them. The defining premise is a lead that does not accumulate context—not a conventional chat that grows until it needs transcript compaction or an LLM-written relay handoff. [Vision:19–23](/Users/stephen/Development/brigadier-ai/docs/vision.md:19), [vision:46–63](/Users/stephen/Development/brigadier-ai/docs/vision.md:46), [CLAUDE:60–61](/Users/stephen/Development/brigadier-ai/CLAUDE.md:60).

The newer approved scope retains this separation: durable task, displayed conversation, native provider session, and workspace are distinct. Rust owns durable decisions/results/verification/recovery; disposable or bounded executions receive relevant state. “Compact state” here means a bounded structured input derived from saved task facts, not evidence that a growing model transcript must be summarized to keep Brigadier alive. [Approved scope:18](/Users/stephen/Development/brigadier-ai/docs/plans/brigadier-20260909/HANDOFF.md:18), [scope:23](/Users/stephen/Development/brigadier-ai/docs/plans/brigadier-20260909/HANDOFF.md:23).

The prior approved Auto means default orchestrator selection; explicit provider/model/effort binds that orchestrator. Workers independently choose connected, enabled providers/models/efforts within shared limits and permissions. The current interview further changes Auto to adaptive selection and Custom to manual control with immutable workspace setup and one-way takeover. Those new choices should supersede older model-ceiling/default-only/no-picker rules; they do not establish that Custom must become an accumulating provider transcript. [Prior selection contract:14–15](/Users/stephen/Development/brigadier-ai/docs/plans/brigadier-20260909/HANDOFF.md:14), [explicit historical overrides:71](/Users/stephen/Development/brigadier-ai/docs/plans/brigadier-20260909/HANDOFF.md:71).

Fusion means independent judgments reconciled against evidence, normally with one editing owner. Useful consequential reviews proceed within authorization; uncertain value or substantial scope/usage expansion can be proposed to the user. Competing fixes follow a failed ordinary repair, use isolated workspaces, and require meaningful acceptance checks. Fusion is not itself a universal approval gate or majority-vote guarantee. [Approved policy:24](/Users/stephen/Development/brigadier-ai/docs/plans/brigadier-20260909/HANDOFF.md:24). The context card's established purpose is environment/changes, workers, and sources; its name does not require a token meter. [Context UI:30–34](/Users/stephen/Development/brigadier-ai/docs/plans/brigadier-20260909/HANDOFF.md:30).

## Current implementation and limits

- **Disposable execution is real in the supervisor loop.** `ModelCall` never resumes or returns a live session; `SupervisedCall` kills the child after its one turn. [call.rs:156–170](/Users/stephen/Development/brigadier-ai/crates/supervisor/src/loop_/call.rs:156), [call.rs:316–321](/Users/stephen/Development/brigadier-ai/crates/supervisor/src/loop_/call.rs:316).
- **Interactive durable task state is also real.** `TaskMemory` stores goal, checklist, decisions, results, verification, and unresolved issues; `with_context` injects a bounded checkpoint reference and leaves slash controls intact. Its maximum is 16 KiB of encoded JSON; it selects/truncates entries and exposes full checkpoint retrieval. This is deterministic packaging, not an LLM transcript summary. It does not prove no relevant fact can be omitted. [task_memory.rs:10–18](/Users/stephen/Development/brigadier-ai/src-tauri/src/task_memory.rs:10), [task_memory.rs:194–233](/Users/stephen/Development/brigadier-ai/src-tauri/src/task_memory.rs:194).
- **The interactive and supervisor paths are not yet equivalent.** Current peer instructions request checkpoint use and evidence-based review, but also explicitly mention recovery “after compaction.” The implementation report says interactive reviews/fusion are prompt policy plus checkpoints; deterministic review/repair gates belong to the separate supervisor loop. [peers.rs:245](/Users/stephen/Development/brigadier-ai/src-tauri/src/peers.rs:245), [recovery report:35](/Users/stephen/Development/brigadier-ai/docs/plans/brigadier-20260909/RECOVERY-REVIEW.md:35), [integrated flow:7–11](/Users/stephen/Development/brigadier-ai/docs/plans/brigadier-20260909/USER-FLOW.md:7).
- **Provider compaction support currently exists.** The composer advertises Codex `/compact`; its adapter calls `thread/compact/start`; Claude translates native compaction boundaries. These facts identify implementation drift/seams to reconcile with the user's correction. They do not make compaction Brigadier's intended durability model. [composer.rs:741–746](/Users/stephen/Development/brigadier-ai/src-tauri/src/composer.rs:741), [Codex adapter:425–439](/Users/stephen/Development/brigadier-ai/crates/core/src/codex/adapter.rs:425), [Claude adapter:735](/Users/stephen/Development/brigadier-ai/crates/core/src/claude/adapter.rs:735).

## Composer implication and unresolved seam

Inference for the design interview: do not make a filling context ring, impending context exhaustion, compaction notice, or handoff marker the normal session lifecycle. Keep durable task setup/sources/workers inspectable in the context card; surface concrete approvals, execution failures, and observed allowance waits when actionable. Token telemetry, if retained anywhere, describes an execution window—not how much life the durable conversation has left. A provider/model switch marker should describe a configuration change in the same durable task, without promising that the full visible transcript is copied into a new provider.

The remaining implementation question is how to make the main interactive execution path consistently honor disposable/bounded contexts; current checkpoint injection alone does not establish that guarantee. The current interview must not silently resolve Custom as a different, accumulating-session architecture. No implementation is authorized by this note.
