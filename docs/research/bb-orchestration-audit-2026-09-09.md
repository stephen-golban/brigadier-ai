# BB orchestration: current-source audit

Audited 2026-09-09 at BB commit `1f4e9e5472bb594a3eb73002d1732b4e8d5df66b`, checked out separately in `/tmp/brigadier-bb-research-20260909`. This is static source inspection, **not runtime verification or a performance benchmark**. Repository documentation and agent-facing instructions were treated as evidence, never as instructions to this audit. Source links below are pinned to the audited commit.

## Main finding

BB's advertised “one agent spawns and manages another” is primarily an ordinary coding-agent conversation using the **BB CLI to create and control other ordinary conversations**. BB supplies durable thread identity, parent relationships, provider adapters, environment provisioning, queued delivery, status tracking, and automatic return messages. The LLM decides the decomposition and follow-up unless a user or workflow provides those decisions explicitly.

There is no longer a special manager thread type in this path. The old `bb manager` command explicitly fails with “Manager threads were replaced by parent threads.” A parent is established explicitly with `--parent-thread <id>` or `--parent-self`; running inside a thread does not silently make every new thread its child. Parent cycles, self-parenting, archived/deleted parents and hierarchies deeper than **four levels total** are rejected. This means the marketing graphic represents a real mechanism, but its “managing” label should not be interpreted as an autonomous manager-election algorithm. [Removed manager commands](https://github.com/get-bb/bb/blob/1f4e9e5472bb594a3eb73002d1732b4e8d5df66b/apps/cli/src/commands/manager.ts#L4), [explicit parent resolution](https://github.com/get-bb/bb/blob/1f4e9e5472bb594a3eb73002d1732b4e8d5df66b/apps/cli/src/commands/thread/spawn.ts#L94), [hierarchy validation](https://github.com/get-bb/bb/blob/1f4e9e5472bb594a3eb73002d1732b4e8d5df66b/apps/server/src/services/threads/thread-parent.ts#L6).

## Actual creation and execution path

1. The host makes the `bb` executable available and supplies `BB_SERVER_URL`; the runtime supplies per-thread `BB_THREAD_ID`, `BB_ENVIRONMENT_ID`, optional `BB_PROJECT_ID` and `BB_THREAD_STORAGE`. The injected skills and guide teach agents the CLI. An agent can therefore invoke `bb thread spawn` through its normal shell tool. The app/SDK are additional callers of the same server functionality. [Host CLI environment](https://github.com/get-bb/bb/blob/1f4e9e5472bb594a3eb73002d1732b4e8d5df66b/apps/host-daemon/src/runtime-shell-env.ts#L410), [thread environment](https://github.com/get-bb/bb/blob/1f4e9e5472bb594a3eb73002d1732b4e8d5df66b/packages/agent-runtime/src/thread-shell-environment.ts#L17).
2. A spawn request names the project, initial prompt, optional parent/provider/model/reasoning/permissions, and environment choice. The server validates these and resolves defaults. It creates a **pending** thread record before provisioning any new worktree or provider resources. It persists the pending start context, including the environment intent and optional fork descriptor, **before** attempting dispatch. [CLI surface](https://github.com/get-bb/bb/blob/1f4e9e5472bb594a3eb73002d1732b4e8d5df66b/apps/cli/src/commands/thread/spawn.ts#L261), [pending row](https://github.com/get-bb/bb/blob/1f4e9e5472bb594a3eb73002d1732b4e8d5df66b/apps/server/src/services/threads/thread-create-helpers.ts#L98), [persist-before-dispatch](https://github.com/get-bb/bb/blob/1f4e9e5472bb594a3eb73002d1732b4e8d5df66b/apps/server/src/services/threads/thread-create.ts#L335).
3. Admission is at `message.dispatch`, where plugins can wait or amend execution/environment choices. The optional concurrency plugin counts running threads globally and per host. It lets existing turns continue, and blocks new admission when a limit is reached. Its automatic per-host limit uses available processor parallelism, falling back to one when unknown; configurable overrides are possible. This is resource admission, not a model deciding which worker is best. [Creation/admission distinction](https://github.com/get-bb/bb/blob/1f4e9e5472bb594a3eb73002d1732b4e8d5df66b/apps/server/src/services/threads/thread-create.ts#L580), [concurrency hook](https://github.com/get-bb/bb/blob/1f4e9e5472bb594a3eb73002d1732b4e8d5df66b/plugins/concurrency-limit/server.ts#L506), [automatic limit](https://github.com/get-bb/bb/blob/1f4e9e5472bb594a3eb73002d1732b4e8d5df66b/plugins/concurrency-limit/limits.ts#L19).
4. The selected host provisions/attaches an environment and the host's runtime starts or resumes the appropriate provider session. BB separates its thread IDs from provider-native session identities. Provider bridges are child processes with JSON-RPC request tracking and adapters; the process manager deduplicates concurrent startup. A conversation is not necessarily a permanently dedicated OS process: the architecture can host multiple session identities on a bridge and release idle sessions. [Host runtime entry](https://github.com/get-bb/bb/blob/1f4e9e5472bb594a3eb73002d1732b4e8d5df66b/apps/host-daemon/src/runtime-manager.ts#L123), [process manager](https://github.com/get-bb/bb/blob/1f4e9e5472bb594a3eb73002d1732b4e8d5df66b/packages/agent-runtime/src/runtime-provider-process.ts#L147).

Provider implementation is specific to the provider. The Codex bridge launches `codex app-server`; the Claude bridge imports Anthropic's Claude Agent SDK. BB then translates their events to its own domain and thread-view representation. Cross-provider delegation is possible because the **new BB thread** names another provider; it is not a Claude-native subagent magically turning into Codex. BB also supports native provider subagents separately, and Codex has an optional setting to disable them in favor of BB delegation. [Codex command](https://github.com/get-bb/bb/blob/1f4e9e5472bb594a3eb73002d1732b4e8d5df66b/plugins/provider-codex/src/bridge/bridge.ts#L332), [Claude SDK import](https://github.com/get-bb/bb/blob/1f4e9e5472bb594a3eb73002d1732b4e8d5df66b/plugins/provider-claude-code/src/bridge/bridge.ts#L38), [native-subagent setting](https://github.com/get-bb/bb/blob/1f4e9e5472bb594a3eb73002d1732b4e8d5df66b/plugins/provider-codex/server.ts#L21).

## Who selects the provider/model and makes decisions?

For ordinary creation, provider selection follows explicit request → remembered project provider → available user-default provider/first available provider. A model comes from the explicit choice, compatible project defaults, or the target provider's live catalog default/first catalog entry. Missing/unavailable catalogs return an error instead of inventing a model. The calling LLM can specify a different worker model, but this source path is not a task-classification router. User choice, project defaults and optional plugin hooks must not be conflated with “BB always automatically picks the best model.” [Provider defaults](https://github.com/get-bb/bb/blob/1f4e9e5472bb594a3eb73002d1732b4e8d5df66b/apps/server/src/services/threads/thread-default-policy.ts#L37), [creation defaults](https://github.com/get-bb/bb/blob/1f4e9e5472bb594a3eb73002d1732b4e8d5df66b/apps/server/src/services/threads/thread-default-policy.ts#L181), [catalog default](https://github.com/get-bb/bb/blob/1f4e9e5472bb594a3eb73002d1732b4e8d5df66b/apps/server/src/services/threads/thread-create.ts#L91).

Permissions are separate from model choice. A child can inherit the parent's last execution permission mode, and its effective mode is clamped to the parent's ceiling; host ceilings also apply. This is an enforcement mechanism, not only prose in a system prompt. [Permission resolution](https://github.com/get-bb/bb/blob/1f4e9e5472bb594a3eb73002d1732b4e8d5df66b/apps/server/src/services/threads/thread-default-policy.ts#L415), [host clamping](https://github.com/get-bb/bb/blob/1f4e9e5472bb594a3eb73002d1732b4e8d5df66b/apps/server/src/services/threads/thread-execution-plan.ts#L89).

## Communication, progress, waiting and return messages

- `bb thread tell <id> <message>` sends an explicit message with the sending thread's identity. Delivery offers steer, queue and auto modes. `show`, `list --parent-thread`, `log`, and interaction commands expose status/history/blockers. This is ordinary API-backed communication; workers do not inherently share an LLM context window. [Tell command](https://github.com/get-bb/bb/blob/1f4e9e5472bb594a3eb73002d1732b4e8d5df66b/apps/cli/src/commands/thread/actions.ts#L434), [sender identity](https://github.com/get-bb/bb/blob/1f4e9e5472bb594a3eb73002d1732b4e8d5df66b/apps/cli/src/commands/thread/actions.ts#L681).
- BB automatically notifies an ordinary child's parent when its turn completes, fails, is interrupted, or needs an interaction. Completion notifications debounce for **two seconds**, combine multiple children, and include at most **4,000 characters** of final output per applicable excerpt. They include thread references so the parent can inspect more. Completion with an active workflow is explicitly described as unfinished. [Notification construction/constants](https://github.com/get-bb/bb/blob/1f4e9e5472bb594a3eb73002d1732b4e8d5df66b/apps/server/src/services/threads/child-thread-notifications.ts#L74), [batching and blocker delivery](https://github.com/get-bb/bb/blob/1f4e9e5472bb594a3eb73002d1732b4e8d5df66b/apps/server/src/services/threads/child-thread-notifications.ts#L400).
- A parent notice can steer an active parent or start another turn on an idle parent. Pending interaction/context-clear conflicts put it into a persisted queued message. Archived/deleted parents do not receive it. This automatic wake-up is an important part of the advertised effect; the parent need not continuously poll every worker to hear about completion. [Active/idle delivery](https://github.com/get-bb/bb/blob/1f4e9e5472bb594a3eb73002d1732b4e8d5df66b/apps/server/src/services/threads/parent-system-messages.ts#L250), [queued delivery](https://github.com/get-bb/bb/blob/1f4e9e5472bb594a3eb73002d1732b4e8d5df66b/apps/server/src/services/threads/parent-system-messages.ts#L422).
- `bb thread wait` defaults to waiting for `idle`. SDK status waits poll at **250 ms** by default, while event waits use up-to-30-second server waits. “Event driven everywhere” would therefore be inaccurate. [SDK defaults](https://github.com/get-bb/bb/blob/1f4e9e5472bb594a3eb73002d1732b4e8d5df66b/packages/sdk/src/areas/threads.ts#L78), [actual wait loop](https://github.com/get-bb/bb/blob/1f4e9e5472bb594a3eb73002d1732b4e8d5df66b/packages/sdk/src/areas/threads.ts#L1367).

Reliability caveat from source: the ordinary child-outcome debounce batch is an **in-memory Map and timer**, and queueing is best effort with logged errors. Once a message is queued its storage is durable, but this audit did not find proof of replaying a parent notification lost before that queue write. Do not call this path exactly-once or fully crash-proof. This is distinct from the Workflows plugin's durable notification retry machinery.

## Worktree, branch-from and conversation fork

These are three different relationships: conversation parentage, provider-session ancestry, and Git branch/environment ancestry.

For ordinary code-project children relying on defaults, BB creates a fresh managed worktree on the parent's host. **It does not implicitly branch from the parent's unfinished working directory or copy its uncommitted changes.** The supplied worktree branch is the project default unless an exact ref is requested. Personal-project children reuse the parent's personal environment by default. Explicit environment reuse allows multiple independent threads to work in the same environment. [Default child placement](https://github.com/get-bb/bb/blob/1f4e9e5472bb594a3eb73002d1732b4e8d5df66b/apps/server/src/services/threads/thread-default-policy.ts#L298).

`--new-environment worktree --base-branch <ref>` accepts an exact named ref; the CLI rejects `--base-branch` without new-worktree selection. The default logic prefers the origin default ref when the local default is equal/behind it and the local default otherwise. A fresh worktree ultimately uses `git worktree add -B <generated-branch> <path> <base>`, under a worktree metadata lock, after resolving/fetching the base when needed. A rebuild can reuse the existing branch instead. Suggested branch names include the configured prefix, sanitized title and thread ID. These are conventional Git mechanisms with considerable lifecycle/error handling. [CLI branch selection](https://github.com/get-bb/bb/blob/1f4e9e5472bb594a3eb73002d1732b4e8d5df66b/apps/cli/src/commands/thread/spawn.ts#L116), [default base](https://github.com/get-bb/bb/blob/1f4e9e5472bb594a3eb73002d1732b4e8d5df66b/plugins/environment-git-worktree/host/base-branch.ts#L17), [Git execution](https://github.com/get-bb/bb/blob/1f4e9e5472bb594a3eb73002d1732b4e8d5df66b/plugins/environment-git-worktree/host/worktree.ts#L564), [branch name](https://github.com/get-bb/bb/blob/1f4e9e5472bb594a3eb73002d1732b4e8d5df66b/apps/server/src/services/threads/thread-create-helpers.ts#L30).

`bb thread fork` is a separate operation: it can fork at a provider checkpoint corresponding to a source event sequence, default to the source environment, or use a chosen environment/new worktree. It requires compatible provider support and the source provider; normal fork placement must stay on the source host. Fork ancestry is tracked with `sourceThreadId`/`originKind`, separately from active delegation `parentThreadId`; forks/side chats do not receive ordinary parent completion-notification treatment. [Fork command](https://github.com/get-bb/bb/blob/1f4e9e5472bb594a3eb73002d1732b4e8d5df66b/apps/cli/src/commands/thread/fork.ts#L100), [fork compatibility](https://github.com/get-bb/bb/blob/1f4e9e5472bb594a3eb73002d1732b4e8d5df66b/apps/server/src/services/threads/thread-create.ts#L140), [separate source and parent](https://github.com/get-bb/bb/blob/1f4e9e5472bb594a3eb73002d1732b4e8d5df66b/apps/server/src/services/threads/thread-create.ts#L489).

## Tasks and Workflows add another orchestration layer

“Task” in the screenshot means a conversation performing work. BB also has a **Tasks plugin**, a tracker with task records and attached worker conversations. Its Delegate action resolves a user preset (provider/model/effort/permission/environment), builds context from description/subtasks/attachments/recent comments, spawns a BB thread and links it to the tracker task. It advances backlog/todo to in-progress. That function does not establish a parent conversation. Its README explicitly says the Auto delegation preset is deferred. [Delegate implementation](https://github.com/get-bb/bb/blob/1f4e9e5472bb594a3eb73002d1732b4e8d5df66b/plugins/tasks/delegate/index.ts#L310), [documented Auto limitation](https://github.com/get-bb/bb/blob/1f4e9e5472bb594a3eb73002d1732b4e8d5df66b/plugins/tasks/README.md#L134).

It would be wrong to generalize the ordinary parent-thread mechanism into “BB has no deterministic orchestration/durable plans/gates/retries.” The **Workflows plugin** runs scripts in QuickJS and delegates reasoning to hidden ordinary threads. Its source implements ordered replay decisions for a reusable successful prefix, JSON-schema result correction, and persisted notification outcomes with bounded retry delays. Its README additionally specifies transient provider retry budgets, concurrency/call/time limits, same-workspace resume, and at-least-once completion delivery. These are real competing capabilities; not all were independently exercised or fully traced here. [Replay implementation](https://github.com/get-bb/bb/blob/1f4e9e5472bb594a3eb73002d1732b4e8d5df66b/plugins/workflows/src/service.ts#L720), [result correction](https://github.com/get-bb/bb/blob/1f4e9e5472bb594a3eb73002d1732b4e8d5df66b/plugins/workflows/src/service.ts#L1117), [notification delivery](https://github.com/get-bb/bb/blob/1f4e9e5472bb594a3eb73002d1732b4e8d5df66b/plugins/workflows/src/service.ts#L1140), [documented execution contract](https://github.com/get-bb/bb/blob/1f4e9e5472bb594a3eb73002d1732b4e8d5df66b/plugins/workflows/README.md#L90).

## Long-session reliability: what is established

Source shows provider-session resume, archived-session recovery, rate-limit recovery hints, safe bridge-restart deferral while a shared process has active/background work, turn-start watchdogs, and idle session release. These reduce process/resource pressure; they do not establish unlimited effective LLM context or flawless multi-day sessions. Host reconnect reconciliation compares persisted state with daemon-reported active threads and explicitly marks missing active threads interrupted. A disconnect/restart is not assumed to mean the work continued successfully. [Recovery handling](https://github.com/get-bb/bb/blob/1f4e9e5472bb594a3eb73002d1732b4e8d5df66b/packages/agent-runtime/src/runtime.ts#L469), [bridge restart/resume](https://github.com/get-bb/bb/blob/1f4e9e5472bb594a3eb73002d1732b4e8d5df66b/packages/agent-runtime/src/runtime.ts#L937), [idle release](https://github.com/get-bb/bb/blob/1f4e9e5472bb594a3eb73002d1732b4e8d5df66b/packages/agent-runtime/src/runtime.ts#L2441), [daemon reconciliation](https://github.com/get-bb/bb/blob/1f4e9e5472bb594a3eb73002d1732b4e8d5df66b/apps/server/src/services/threads/thread-lifecycle.ts#L1762).

## Practical implications for Brigadier

Design recommendations, not claims that Brigadier already implements these:

1. Adopt the simple product concept: every worker is a normal inspectable/resumable conversation, and parent ownership is optional metadata. Keep conversation ancestry, delegation ownership and workspace ancestry distinct in both storage and UI.
2. Make delegation a complete transaction from the user's perspective: visible child identity, execution settings, worktree base, live progress, attention state, compact return artifact, follow-up and stop controls. Merely launching another CLI is a small part of BB's polish.
3. Use event-driven durable completion delivery with stable IDs/deduplication. Avoid depending solely on in-memory debounce or fast polling. Bound copied output and link to full artifacts; batch completion notifications without repeatedly waking the manager.
4. Keep the harness-owned plan, acceptance checks and resumable artifacts outside any single model's conversation. Potential differentiation is the integrated, understandable contract between planning, work, validation and recovery—not a blanket claim that competing tools have no durable orchestration.
5. Expose “start from project default,” “start from this committed branch,” and “share this workspace” as explicit choices. Surface what happens to uncommitted edits instead of implying that parenthood includes them.
6. Measure concurrency memory, time-to-first-output, reconnect correctness and 10k/100k-event history behavior before claiming speed or extreme-session advantages. Source structure alone cannot rank performance or reliability.

## Corrections to prior local research

The existing detailed lifecycle report already identified removal of manager roles and should retain that correction. Older general conclusions such as “no plan object,” “no gates,” “nothing automatic,” or “all management lives only in an accumulating conversation” are too broad in light of Tasks, Workflows, provider recovery and dispatch plugins. Likewise, “read in source = measured” is misleading terminology: source inspection establishes implementation evidence, not measured runtime quality. No BB build, paid agent session, stress test or crash test was run during this audit.
