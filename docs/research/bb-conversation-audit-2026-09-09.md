# BB conversation, UI and long-session audit

Reviewed 2026-09-09. BB commit `1f4e9e5472bb594a3eb73002d1732b4e8d5df66b`; Brigadier working tree at HEAD `289f63d0cb131ee8cbf62cc7494ed0183295462a`. Official assistant-ui pages linked below were fetched and read through the web tool; canonical HTML worked where `.md` endpoints failed. This is a source audit, not a measured comparison of the running apps. Existing research notes were not treated as proof. No product code changed.

BB's conversation is custom React UI backed by a purpose-built event-to-timeline projection. It is not an undisclosed chat framework that Brigadier needs to acquire. Brigadier already has assistant-ui and an external-store adapter. The useful next work is completing its data/stream integration, bounded history and interaction behavior, then refining visual density.

## How the timeline stays manageable

**Separate canonical events from presentation.** BB's shared projection exports `buildThreadTimelineFromEvents` and `buildTimelineViewRows`. Conversation rows carry stable ID, thread/turn IDs and source sequence ranges. This lets presentation group work while preserving its originating events. [Shared timeline projection](https://github.com/get-bb/bb/blob/1f4e9e5472bb594a3eb73002d1732b4e8d5df66b/packages/thread-view/src/index.ts#L45) [Row identity contract](https://github.com/get-bb/bb/blob/1f4e9e5472bb594a3eb73002d1732b4e8d5df66b/packages/server-contract/src/thread-timeline.ts#L68)

**Read recent windows and fetch older history.** Server defaults to 20 segments with a maximum request of 100 and an event-data budget of 4 MiB. A segment is not necessarily a message: do not describe this as “20 messages.” Compact viewports request eight segments. Clients send `afterSequence` from the prior `maxSeq`, apply a returned timeline delta and fall back to a full window if the delta cannot merge. Older rows load through a scroll sentinel with a 600px prefetch margin and capture the current scroll anchor before prepending. [Timeline bounds](https://github.com/get-bb/bb/blob/1f4e9e5472bb594a3eb73002d1732b4e8d5df66b/apps/server/src/services/threads/timeline.ts#L144) [Timeline delta reads](https://github.com/get-bb/bb/blob/1f4e9e5472bb594a3eb73002d1732b4e8d5df66b/apps/app/src/hooks/queries/thread-queries.ts#L880) [Older-history loading](https://github.com/get-bb/bb/blob/1f4e9e5472bb594a3eb73002d1732b4e8d5df66b/apps/app/src/components/thread/timeline/useAutoLoadOlderRows.ts#L4)

**Bound caches and heavy outputs.** Timeline cache defaults to 128 entries and does not cache responses over 200 rows; a separate latest-rows cache defaults to 64 entries. Command/tool outputs over 4,000 UTF-16 code units are previewed as a 2,000-unit head plus 1,000-unit tail. Detail loading has explicit complete, streaming, limited and expired-preview states, so “full output” is not guaranteed forever. A separate default inline output truncation limit is 32,000. These are different layers, not one global transcript cap. [Timeline cache](https://github.com/get-bb/bb/blob/1f4e9e5472bb594a3eb73002d1732b4e8d5df66b/apps/server/src/services/threads/timeline-cache.ts#L5) [Latest cache](https://github.com/get-bb/bb/blob/1f4e9e5472bb594a3eb73002d1732b4e8d5df66b/apps/server/src/services/threads/timeline-latest-rows-cache.ts#L3) [Output preview](https://github.com/get-bb/bb/blob/1f4e9e5472bb594a3eb73002d1732b4e8d5df66b/apps/server/src/services/threads/timeline-output-preview.ts#L4) [Output availability states](https://github.com/get-bb/bb/blob/1f4e9e5472bb594a3eb73002d1732b4e8d5df66b/apps/app/src/components/thread/timeline/useTimelineWorkRowFullOutput.ts#L14) [Inline truncation](https://github.com/get-bb/bb/blob/1f4e9e5472bb594a3eb73002d1732b4e8d5df66b/apps/server/src/services/threads/timeline-output-truncation.ts#L3)

**Coalesce streaming changes.** The provider delta assembler defaults to a 100ms text flush threshold and 500ms progress throttling. It emits the first delta immediately, buffers subsequent text by item/channel and flushes at boundaries; the threshold is implementation policy, not a measured end-to-end latency. UI realtime invalidation is also paced: fine-pointer defaults 50ms debounce / 200ms maximum wait, coarse pointer 150ms / 400ms. Queries subscribe to thread detail changes. This is change notification plus bounded fetch/delta merge, rather than assuming every token is directly rendered from a WebSocket. [Assembler defaults](https://github.com/get-bb/bb/blob/1f4e9e5472bb594a3eb73002d1732b4e8d5df66b/packages/provider-bridge-protocol/src/assembler/delta-assembler.ts#L208) [Text buffering](https://github.com/get-bb/bb/blob/1f4e9e5472bb594a3eb73002d1732b4e8d5df66b/packages/provider-bridge-protocol/src/assembler/delta-assembler.ts#L330) [Invalidation pacing](https://github.com/get-bb/bb/blob/1f4e9e5472bb594a3eb73002d1732b4e8d5df66b/apps/app/src/hooks/realtime-cache-effects.ts#L42) [Timeline delta reads](https://github.com/get-bb/bb/blob/1f4e9e5472bb594a3eb73002d1732b4e8d5df66b/apps/app/src/hooks/queries/thread-queries.ts#L880)

**Keep settled markdown separate.** While generating, BB splits settled content from the live tail and repairs/parses that tail. At completion it can render the finished document. Memoization exists both at row and markdown layers. This is a specific optimization worth studying; it does not establish that BB is faster than Brigadier on a workload we have not measured. [Live markdown split](https://github.com/get-bb/bb/blob/1f4e9e5472bb594a3eb73002d1732b4e8d5df66b/apps/app/src/components/thread/timeline/ConversationMessageContent.tsx#L511) [Markdown renderer](https://github.com/get-bb/bb/blob/1f4e9e5472bb594a3eb73002d1732b4e8d5df66b/apps/app/src/components/ui/markdown-preview.tsx#L1675)

**Virtualization exists, but is experimental and disabled by default.** `timelineWindowing` is false in the canonical experiment defaults and the timeline surface reads that flag. When enabled, TanStack Virtual uses overscan eight and a bounded 2,000-entry measurement map; top-level activation thresholds are 60 items desktop / 40 compact, nested lists 20. It keeps the latest row, unread divider, search targets, restored anchor and navigation target mounted, and pins interacted rows. Simply installing a virtualizer does not preserve these behaviors automatically. [Experiment defaults](https://github.com/get-bb/bb/blob/1f4e9e5472bb594a3eb73002d1732b4e8d5df66b/packages/domain/src/experiments.ts#L21) [Windowing flag use](https://github.com/get-bb/bb/blob/1f4e9e5472bb594a3eb73002d1732b4e8d5df66b/apps/app/src/components/thread/timeline/ThreadTimelineSurface.tsx#L180) [Windowing implementation](https://github.com/get-bb/bb/blob/1f4e9e5472bb594a3eb73002d1732b4e8d5df66b/apps/app/src/components/thread/timeline/TimelineWindowedItems.tsx#L20) [Pinned rows and thresholds](https://github.com/get-bb/bb/blob/1f4e9e5472bb594a3eb73002d1732b4e8d5df66b/apps/app/src/components/thread/timeline/ThreadTimelineRows.tsx#L1854)

**Provider context and UI history are distinct.** Codex standalone `/compact` dispatches `thread/compact/start`; Codex and Claude compaction events are translated. This documents integration with provider compaction, not an unlimited context window or demonstrated multi-week reliability. UI output previews and row windowing solve rendering/data volume; they do not ensure that the agent remembers the task after compaction. [Codex compact request](https://github.com/get-bb/bb/blob/1f4e9e5472bb594a3eb73002d1732b4e8d5df66b/plugins/provider-codex/src/bridge/bridge.ts#L1453) [Claude compaction events](https://github.com/get-bb/bb/blob/1f4e9e5472bb594a3eb73002d1732b4e8d5df66b/plugins/provider-claude-code/src/delta-translation.ts#L624)

## What is already in Brigadier, and the gaps

The dependency is already installed: `@assistant-ui/react ^0.15.18`, React 19 and TanStack Virtual 3.14.10. [package.json](/Users/stephen/Development/brigadier-ai/package.json:15)

`ThreadView` uses `useExternalStoreRuntime`, maps projected rows to assistant-ui messages and wires send/cancel to the bridge. However, its comment explicitly says the runtime owns only viewport behavior. Work rows become empty-content assistant messages for the adapter, and the actual transcript bypasses message primitives through a direct `rows.map`, rendering standalone Elements and custom `WorkTrace`. This is a partial integration, not absence of the library. [ThreadView](/Users/stephen/Development/brigadier-ai/src/components/ThreadView.tsx:295)

The visible transcript starts its read cursor at zero, requests saved chat plus all turn records, immediately drains pages of 20, polls every 700ms once caught up and retains only the last 2,000 loaded items. It sorts/rebuilds the array when a page arrives. The shown rendering path has no row virtualizer or load-older affordance. Consequences inferred from this path: long histories require startup replay, old loaded rows disappear from this view after the cap, and repeated turn-record reads add avoidable work. The persisted database may retain more; this is a UI behavior finding, not a claim of deletion. [Read loop](/Users/stephen/Development/brigadier-ai/src/components/ThreadView.tsx:235) [Rendering](/Users/stephen/Development/brigadier-ai/src/components/ThreadView.tsx:391)

The viewport already supplies scroll restoration, jump-to-latest and persisted expansion state. Its standalone adapter uses an 820px content column and disables scroll-to-bottom-on-run-start. Those are useful foundations. [Viewport adapter](/Users/stephen/Development/brigadier-ai/src/components/assistant-ui/elements/thread.tsx:19) [Restoration](/Users/stephen/Development/brigadier-ai/src/components/ThreadView.tsx:199)

## assistant-ui fit, verified against official docs

**Keep the external-store runtime.** It is explicitly for applications that own message state, persistence and synchronization. Supply stable IDs and immutable updates, preserve tool-call IDs, provide only capabilities the backend supports, and keep selected thread identity synchronized. Editing, cancellation, branch switching and tool-result handoff are enabled by corresponding callbacks. This matches Brigadier better than adopting a second chat backend. [ExternalStoreRuntime](https://www.assistant-ui.com/docs/runtimes/custom/external-store)

**Represent the conversation as structured parts.** Use text for user-facing prose; tool parts with status and structured result references for commands, file edits, tests and peer tasks. Custom tool renderers can display running/result/interactive states. Message part grouping provides a way to collapse contiguous work under one expandable activity section. It cannot infer correct turn boundaries from lossy text rows; the provider/event projection must supply them. [Tool UI](https://www.assistant-ui.com/docs/tools/tool-ui) [Part grouping](https://www.assistant-ui.com/docs/guides/part-grouping)

**Do not confuse subagent UI with orchestration.** `MessagePartPrimitive.Messages` renders a tool part's nested messages recursively and inherits tool renderers, but the documented nested context is read-only: no editing, branching or composing. Brigadier still owns launching CLIs, worktree isolation, mailbox delivery, supervisor policy, durable task state and cancellation. Use compact child-task cards linking to independently selectable task views; expand inline messages only when useful. [Multi-agent UI](https://www.assistant-ui.com/docs/tools/multi-agent)

**Use the viewport deliberately.** Current docs provide auto-scroll that respects user scrolling, top turn anchoring and a registered footer. They also expose `MessageByIndex` and experimental `Unstable_MessageById` / `unstable_useThreadMessageIds` for custom windowed lists. Ordinary `Messages` iterates messages; the docs do not establish automatic production-ready virtualization. Verify these APIs against the installed version and isolate unstable use behind an adapter. [Thread primitives](https://www.assistant-ui.com/docs/primitives/thread)

**Conversation branches are not Git branches.** assistant-ui's `parentId`/branch repository selects alternative message paths; Git worktree/branch ownership remains Brigadier backend state. Connecting those concepts should be an explicit product decision, never inferred from a BranchPicker control. [ExternalStoreRuntime branching](https://www.assistant-ui.com/docs/runtimes/custom/external-store#branching)

## Recommended order and acceptance evidence

These are engineering recommendations, not implemented changes or benchmark results.

1. Define stable turn/item/part identity and replay ordering. Enable real Claude deltas and reconcile final snapshots without duplicated prose; expose rate-limit and compaction status. Ensure one authoritative store drives both runtime and visible rows.
2. Add latest-window loading, backward cursors and targeted turn updates. Preserve full searchable persisted history separately from the bounded in-memory view. Put large outputs behind previews/detail loading with clear retention state.
3. Add windowing while preserving reading position, focused/expanded rows, active tasks, unread markers and message search. Narrow store subscriptions and update only changed rows. Split settled markdown from the live tail where profiling justifies it.
4. Refine the conversation: plain assistant prose, restrained user blocks, one compact activity group per turn, expandable command/diff details, a child-task card with provider/status/result and explicit open/stop actions, and a durable “needs input” state. These are suggested interaction choices, not claims about proprietary ChatGPT/Codex source.
5. Validate with recorded provider fixtures plus native runs: 10,000 events, very large command output, 20 synthetic worker streams (or real workers spread across projects while respecting current concurrency limits), repeated task switches, prepend-history while scrolled, stop during streaming, reconnect after missed events, restart during a running turn and multiple context compactions. Measure time-to-latest, per-delta render cost, DOM count, memory slope and event/replay correctness. Set success budgets after collecting a baseline; do not promise fixed improvements first.

This audit did not run BB, benchmark either app, or recover ChatGPT/Codex's private frontend. Its strongest conclusion is architectural: Brigadier can improve this experience incrementally using the library it already has, while borrowing BB's bounded projection and display policies rather than replacing its whole stack.
