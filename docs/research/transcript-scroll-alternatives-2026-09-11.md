# Transcript scrolling alternatives — 2026-09-11

**Recommendation: conditional second alternative, not the next assumed fix.** Replacing the synthetic writable transcript runtime with app-owned scrolling is architecturally supported, but no measurement establishes it as the remaining 45 ms culprit. The parent’s older hydrated-runtime trace was approximately 3 ms. Removing it cannot be claimed to recover the entire frame, and replacing scrolling introduces real behavior work. Prefer investigating the measured parent-update path first; consider a bounded viewport experiment only if a fresh attribution shows material runtime cost.

## What requires a runtime

[Official Chat Panel Elements](https://www.assistant-ui.com/elements/chat-panel) support props-driven composition without a runtime. The installed [ChatPanel and ChatPanelMessages](/tmp/brigadier-performance-fix-20260911/src/components/assistant-ui/elements/chat-panel.tsx:11) are styled divs; the latter supplies native overflow scrolling. They accept custom DOM children, but contain no follow/restore/jump logic. The official full [Thread element](https://www.assistant-ui.com/elements/thread) is runtime-connected and has no standalone equivalent.

[Brigadier’s Thread adapter](/tmp/brigadier-performance-fix-20260911/src/components/assistant-ui/elements/thread.tsx:20) wraps those divs with ThreadPrimitive.Root, Viewport, ViewportFooter and ScrollToBottom. [Installed auto-scroll](/tmp/brigadier-performance-fix-20260911/node_modules/@assistant-ui/react/src/primitives/thread/useThreadViewportAutoScroll.ts:59) reads thread messages/running state and subscribes to run-start and thread-selection events. It therefore needs appropriate AUI scopes; **useExternalStoreRuntime specifically is not mandatory**, nor is that hook solely a scrolling API. [ExternalStoreRuntime documentation](https://www.assistant-ui.com/docs/runtimes/custom/external-store) describes a complete message/state/capability adapter.

[ThreadView](/tmp/brigadier-performance-fix-20260911/src/components/ThreadView.tsx:334) already renders saved rows directly, while constructing a second message representation for [TranscriptRuntime](/tmp/brigadier-performance-fix-20260911/src/components/TranscriptRuntime.tsx:23). Current actual [Composer](/tmp/brigadier-performance-fix-20260911/src/components/Composer.tsx:125) uses its supplied onSend; [App](/tmp/brigadier-performance-fix-20260911/src/App.tsx:1308) directly supplies bridge send/interrupt behavior. The inspected production source has no useAui composer caller; the synthetic runtime’s composer capabilities are exercised by tests. Removing that contract is still an intentional interface change, not proof it never matters.

Markdown is a separate dependency: [TextMessagePartProvider](/tmp/brigadier-performance-fix-20260911/node_modules/@assistant-ui/core/src/react/providers/TextMessagePartProvider.tsx:44) calls useAui and creates a part-scoped provider. Keep an appropriate minimal AuiProvider around that content rather than declaring all provider infrastructure removable. Preserve the existing read-only branch/capability restrictions; no direct-runtime migration is needed for this scrolling alternative.

## Obligations of a replacement

- Preserve the same DOM dimensions, overflow element, forwarded ref and TanStack virtualizer measurements. Restore the saved non-following position only after hydration; initial following must reach the real loaded bottom. Avoid persisting transient empty-state offsets. [Current restoration/persistence](/tmp/brigadier-performance-fix-20260911/src/components/ThreadView.tsx:357).
- Continue following only while the user intends it. Do not force a jump on busy/run-start: current configuration explicitly disables that trigger. Distinguish upward user scroll from content-induced scroll shifts, preserve pending bottom intent while content does not yet overflow, and handle pointer interaction during pending scrolling. [Installed scroll logic](/tmp/brigadier-performance-fix-20260911/node_modules/@assistant-ui/react/src/primitives/thread/useThreadViewportAutoScroll.ts:124).
- Respond to streaming DOM changes and viewport/content resizing, including async Markdown, attachments, expanded cards, pane resize and virtualized row size correction. A layout effect depending only on React children does not cover those changes. Avoid observer/write feedback and cancel scheduled work on unmount. [Installed resize/mutation observation](/tmp/brigadier-performance-fix-20260911/node_modules/@assistant-ui/react/src/utils/hooks/useOnResizeContent.ts:6).
- Preserve accessible Jump to latest, its visibility and resumption of following, smooth-scroll intent handling, and sticky-footer geometry. Library at-bottom tolerance is about 1 px; app persistence uses 64 px. Do not silently replace both with one threshold. [Installed jump action](/tmp/brigadier-performance-fix-20260911/node_modules/@assistant-ui/react/src/primitives/thread/ThreadScrollToBottom.ts:18), [metrics](/tmp/brigadier-performance-fix-20260911/node_modules/@assistant-ui/store/src/utils/viewport-scroll.ts:12).

The existing ReadonlyViewport is useful structural precedent, **not** a ready writable replacement: it follows on children changes and lacks the writable observer behavior and Jump to latest control. Top-anchor behavior need not be implemented because this app uses bottom anchoring. A scoped experiment should preserve actual initial rendering and full feed delivery, with focused restore/follow/resize/jump checks; broad rewrites or repeated full test loops are not justified by this source audit.

Research only: no application changes, builds, tests, captures or UI actions.
