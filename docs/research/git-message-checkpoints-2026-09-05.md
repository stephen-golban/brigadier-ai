# Git-backed message checkpoints: research and proposed design

## Recommendation

**[proposal] Use a separate app-owned bare Git snapshot repository, outside the workspace, with raw file blobs, temporary indexes, trees and explicit retention refs. Capture before each human message and after its entire writing activity has settled. Keep conversation rewind provider-native.** Do not store checkpoint refs in the user's repository, copy their index as a workspace snapshot, or restore through `reset`, `clean`, `checkout` or provider file rewind.

**[measured]** The primitives work on installed Git **2.50.1 (Apple Git-155)**. Raw capture preserves binary/CRLF bytes, empty files, symlink targets and executable modes. Alternate indexes preserve the original staged index and HEAD. Seven-path selective restoration preserved staged plus unstaged baseline content and an unrelated later manual file. Identical snapshots and write-then-undo sequences produced equal trees. Full reproducible results: [experiment script](git-checkpoint-experiments-2026-09-05.py), [JSON results](git-checkpoint-experiments-2026-09-05.json). Independent research: [primary-source report](git-checkpoint-primary-sources-2026-09-05.md).

**[proposal] Confirm this bounded v1 contract:** restore net changes in declared checkpoint coverage, preserve unrelated manual paths and pre-existing staged/unstaged work, and block on overlapping edits, incomplete history, uncertain writers, or source Git-state changes. Automatically rewind/resend when the verified final restore plan is empty, including unchanged message text. If the plan changes files, show its exact operations and retain a recovery checkpoint before applying it. A conflict is not an empty plan.

**[measured + inference]** Git snapshots cannot attribute simultaneous external writes or provide an atomic filesystem snapshot. A deterministic scan captured `(a=0,b=1)` although actual states were only `(0,0)`, `(1,0)`, `(1,1)`. An isolated Git worktree reduces workspace sharing but does not prevent external processes from writing it. An unconditional promise to preserve every simultaneous manual edit is therefore unsupported. Stronger guarantees require enforcing write isolation beyond Git.

## Supported scope and ownership

Everything in this section is **[proposal]**.

- Each checkpoint belongs to a stable workspace ID plus canonical root identity; record resolved source worktree/gitdir/common-dir identity when applicable. Reject path substitution, root moves or repository replacement until reconciled. Distinct linked worktrees get separate filesystem epochs; shared repository metadata changes still invalidate affected guards.
- Normal coverage: tracked regular files/symlinks and nonignored untracked equivalents, plus explicitly included ignored paths. Hard exclusions override tracking: Git administration, Brigadier state/worktrees, configured secrets, dependency/build caches and paths outside the root. Choose and persist the exact policy before activation; silently skipping a file on error is forbidden. For non-Git roots require an explicit coverage policy rather than treating every hidden file as safe to copy.
- Freeze ignore/exclusion classification for each coverage epoch, including rules for new paths. Changing `.gitignore` during a turn must not make an existing included file disappear from coverage and look deleted. Record exclusions separately from `incomplete` errors (unreadable, quota/size limit, unstable file, unsupported type). A policy change starts a new coverage epoch; v1 refuses rewinds across incompatible epochs.
- Product wording is “checkpointed files,” with coverage available beside capability status. An intentional exclusion does not make a supported-scope snapshot incomplete, but it prevents any claim that the entire workspace or external effects were restored. If Stephen wants ignored generated files included by default, that changes the scope and storage budget before implementation.
- Preserve original staged state by never writing the source index. Capture working bytes, not HEAD, as the before-image; this preserves existing unstaged edits too. Record semantic index entries/stages/flags and byte fingerprint, source HEAD/ref, conflict/operation state and sparse state. Benign stat-cache rewrites can be distinguished later; v1 may conservatively reject a byte-fingerprint change. Do not restore opaque index bytes: split-index/shared files and Git state need their own design.
- Source commits, branch switches, staging/unstaging, merge/rebase/conflict changes across an affected epoch or after preview block v1 combined restore. Compare every recorded boundary, not only earliest and latest. Endpoint fingerprints cannot detect a change and reversal during the epoch; actor ownership remains an assumption, not an attribution detector. Conversation-only editing can remain separately available with explicit “files retained” semantics.
- All Brigadier writers sharing one canonical workspace must coordinate: session sends, child work, verification commands, merge operations, cleanup, rewinds and app processes. Use an app-level workspace lease; `git worktree lock` is not a file-write lock. Capture may coexist with independent workspaces, but a rewind must exclude every app writer for its workspace.
- Direct/shared checkout support requires the same exclusive writing interval as an isolated worktree. External editors can safely change unrelated paths while the app is idle; same-path changes are preserved by rejection when detectable. Uncontrolled simultaneous writers are outside the restoration guarantee. If the owner needs guaranteed concurrent manual editing, enable capture-only/conversation-only there and restrict combined restore to enforceably isolated execution. Do not silently infer exclusivity from the existence of a worktree.
- No automatic content merge in v1. Whole-path conflicts preserve both current and checkpoint bytes for review. File/directory topology collisions block the operation; do not recursively delete unknown descendants. Symlink, hardlink and special-file handling requires the checks in the acceptance tests before enabling those restore cases.

## Checkpoint timing and plan calculation

Everything in this section is **[proposal]**, supported by the per-turn fixture experiments.

1. Reserve a local operation/turn ID before dispatch. Acquire the workspace lease and adapter dispatch barrier. Verify the prior epoch has settled. After the actual session cwd is resolved, capture `pre(message)` and durably publish its ref and metadata **before sending any user frame**. Checkpoint failures leave the draft unsent in checkpoint-required mode; a separate explicit conversation-only capability may continue without restore support.
2. Route the first prompt through this path too. For interactive sessions, start the provider without `config.prompt`, install supervision, then dispatch through the prepared path. Record a separate launch baseline before spawn if startup-hook changes are to be recoverable; startup effects before the human pre-snapshot are not retroactively that message's changes. Internal one-shot orchestration prompts must either use the same seam or be labeled outside this feature.
3. Bind the reserved ID to local human row and the verified provider replay UUID. A write/transport failure may have partially delivered a prompt: persist `send_pending/send_unknown`, retain the pre-checkpoint, and do not retry blindly. A definite refusal without delivery can release the lease. Existing provider UUID verification stays authoritative.
4. `post(message)` is after all main/subagent/background writing associated with that human epoch, terminal hooks and supervised child processes have quiesced, with events flushed. A `result` alone is insufficient: existing provider evidence shows one human prompt can produce several result frames. Prevent a next message from pre-empting an unfinished checkpointed epoch. Missing/unknown task lifetime, unowned late activity or crash means incomplete, not empty. A resumed current snapshot cannot reconstruct a missing historical post snapshot.
5. At edited Send, obtain a fresh current snapshot `C`, every complete `pre_i/post_i` pair in the discarded span, source Git-state guards, coverage version and provider transcript revision. A 2,000-row UI history cap must not limit this query: query checkpoint metadata and authoritative transcript cursors directly.
6. For each path, group chronological epochs into continuous segments: every prior `post(path)` must equal the next `pre(path)`, including no-op epochs. Split at idle/manual value changes; reject incomplete/coverage/Git-state gaps before grouping. Drop a segment only when its first pre-state equals its last post-state. Thus `A→B→A` has no undo even if a later manual edit leaves `D`; never cancel across an idle gap such as `A→B; C→A`. Keep individual transitions in nonzero segments so partial prior undo remains recognizable. Construct virtual `V=C` and visit retained transitions newest first: if `V==post`, set `V=pre`; if `V==pre`, skip; otherwise conflict. Equality includes absence/type/raw blob/mode. Validate final topology; any conflict blocks all real writes.
7. The concrete restore plan is `diff(C,V)`, after all epochs compose. An empty plan with complete compatible checkpoints and satisfied ownership guards goes straight through native rewind and edited send, even if text is unchanged or intermediate writes occurred. Otherwise confirmation lists exact restore/create/delete/type/mode operations, optional escaped diff, bytes for binary files, and recovery availability. It does not show the union of historical tool writes.

Why paired boundaries matter: turn 1 changes `agent:A→B`; an idle manual edit changes `manual:M0→M1`; turn 2 changes `agent:B→C`. Reversing the two turn deltas yields `agent:A, manual:M1`. Restoring the earliest whole tree yields `manual:M0` and loses the manual edit. This distinction is **[measured]**. Same-path manual edits may make reversal ambiguous; retain them and block rather than guess intent.

The preview ticket binds workspace identity, coverage generation, checkpoint refs/OIDs, ordered epoch IDs, provider target/latest UUID, transcript sequence, current manifest/Git-state fingerprint, and exact planned operations. Release locks while the person reviews. On confirmation reacquire them and revalidate; any intervening change invalidates the ticket. Recompute and require a fresh confirmation if changed operations would apply. An empty replacement plan can take the normal no-confirmation path.

## Transaction and recovery

Everything in this section is **[proposal]**. Git, SQLite, filesystem writes and a running provider have no shared atomic transaction. Prefer **files first, then native conversation rewind**, because files have app-owned before-images while the provider's conversation mutation has no verified inverse. This order needs explicit compensation; it does not eliminate partial outcomes.

| Durable phase | Action | Failure / restart behavior |
|---|---|---|
| `prepared` | Under workspace lease and adapter barrier, revalidate ticket including paths used in no-op reasoning. Retain current recovery tree and all objects needed for `V`. Flush transcript archive and transaction record with provider target, draft, immutable plan and source-state guards. | No mutation before durable recovery is verified. Missing objects, disk full, unstable paths or archive failure leave conversation/files unchanged. Orphan published refs can be reconciled later. |
| `files_applying` | Stage raw target bytes from `cat-file blob` in safe temporary siblings; journal each path's expected current value and intended target before replacement/deletion. Check identity/type/content immediately before each write. Record progress and verify result manifest. | No broad cleanup. Stop on mismatch or I/O failure. Recover from per-path journal; do not start provider rewind until the entire plan verifies. |
| `files_applied` | Flush files/directories and journal; persist native request intent before sending `rewind_conversation` with target UUID and latest-human guard. An empty plan follows the same durable provider journal without file writes. | A crash before request intent permits guarded file compensation. A crash after intent must be treated as potentially sent; no blind retry. |
| `provider_refused` | Only a classified authoritative refusal follows this path. Keep displayed transcript. Compensate file operations using recovery bytes. | Reverse only actual journaled writes, requiring current value to equal the value this operation applied (or already equal its original value). Any mismatch blocks compensation and retains recovery; never overwrite a new manual edit. |
| `provider_unknown` | Timeout/EOF/unrecognized target or response, missing durable response, or uncertain provider persistence. | Keep files as observed, retain both snapshots/archive, block sends and resume. Do not automatically roll files back when native rewind may have succeeded. Raw provider JSONL presence cannot settle this. |
| `provider_applied` | Verify exact target and adapter response-time sequence. Durably record known native success, then archive/cut local transcript through that sequence using existing late-row suppression. | Storage failure remains blocked; recording success and finishing local history are separate states. Do not repeat native rewind just because local finalization failed. |
| `ready_to_send` | Keep ownership; reserve the edited message's new turn/provider ID, then capture and durably bind its **new** pre-checkpoint from the restored workspace. Preserve its draft. | Capture failure leaves a completed rewind awaiting send. Retry must not rewind again. |
| `send_pending` → `sent` | Dispatch the edited text through the prepared provider path. Transfer the workspace lease into the new writing epoch without a race for another sender. Record dispatch/replay outcome. | Definite non-delivery is retryable using the prepared ID only under verified adapter semantics. Unknown delivery blocks blind resend. Native rewind completion alone does not prove edited text was delivered. |

**[proposal]** Startup scans unresolved records before any provider is resumed or workspace writer started. File recovery compares each current path with its journaled old/new states and refuses a third value. Equality to a target proves file state only, never whether native rewind ran. Expose recovery ID, known phase, original transcript and recoverable path versions; manual reconciliation of native ambiguity remains necessary until a separately verified provider recovery reader exists.

**[proposal]** Avoid symlink traversal and hardlink writes: descriptor-relative, no-follow directory traversal; reject absolute/parent traversal/Git-admin paths; validate root and ancestor identity again during apply. Replacing a regular-file entry must not truncate another hardlinked path. Preserve existing ACL/xattr semantics or refuse unsupported entries rather than silently stripping them. Apply only enumerated paths, never recursively remove a directory containing unplanned files. Atomic rename is per path, not an atomic multi-file restore, and a precheck alone does not prevent a noncooperating writer racing it.

**[documented]** `cat-file` exposes raw blobs; transformations are opt-in flags ([cat-file](https://git-scm.com/docs/git-cat-file)). **[proposal]** Use raw OIDs, not path-derived revision expressions supplied by UI. Validate object kinds and hashes on recovery, and do not enable `--filters`, textconv, external diff or checkout-based restore.

**[unchecked]** This task did not run a crash/power-loss test or integrate a provider rewind with file restoration. Git ref success is not proof that object, ref, journal, file and directory data all survive power loss. The implementation must select and test durability settings on the minimum supported Git/filesystem; no claim of cross-platform durability follows from these experiments.

## Storage, performance and security

**[proposal]** Suggested layout: `<app-data>/checkpoints/<workspace-id>/objects.git`, separate temporary-index/staging directories, SQLite checkpoint/epoch/rewind metadata. Use direct tree refs such as `refs/checkpoints/<checkpoint-id>` and `refs/recovery/<operation-id>`. No parent chain is needed: each tree is an independent retention root; a chain of commits would retain older checkpoints through ancestry. Persist hash algorithm/version in metadata; do not bake 40-character SHA-1 assumptions into APIs.

**[proposal]** Use a dedicated Git command runner with an explicit bare gitdir and task-owned index. Clear inherited Git repository/object/index/config override variables, suppress system/global config for store operations, initialize from an empty template, disable hooks and fsmonitor, and keep store config app-owned. Never execute source-repository clean/smudge/process/reference hooks while capturing or restoring. Reading source classification/Git-state needs a separately hardened read-only path and must not trigger fetch/LFS hydration. The source worktree helper already contains filter/fsmonitor mitigations, but it is not a general snapshot command runner.

**[documented]** `init` can copy templates ([init](https://git-scm.com/docs/git-init)); ref transactions can invoke hooks ([githooks](https://git-scm.com/docs/githooks)). **[proposal]** Therefore raw plumbing alone is not a hook-execution defense. Run from app-controlled directories, use argument arrays rather than a shell, sanitize stored/displayed path names, restrict store directory permissions, and never configure a remote. Snapshots can contain secrets even when files are Git-ignored; secret exclusions must be explicit and apply to tracked files too. Local storage is not encryption or a sandbox against a provider running as the same OS user.

**[measured]** [JSON benchmark](git-checkpoint-experiments-2026-09-05.json): **1,000 files × 1,024 bytes = 1,024,000 bytes**; capture times **460.53 / 99.57 / 93.24 ms**, first/repeated/repeated. The object store remained **60,913 bytes** after each identical snapshot (including earlier fixture objects). Capture includes batch raw hashing, index construction and ref publication, but excludes fsync, ignore evaluation, race checks, UI, large binaries and cold-disk behavior. This is a small synthetic primitive benchmark, not product latency. Benchmark batching uses newline-free paths; the fidelity fixture separately covers tab/newline paths using raw stdin bytes and NUL index records.

**[proposal]** Benchmark bounded raw-object batching rather than a subprocess per file. Full scans remain the baseline; watchers are invalidation hints and mtime alone cannot prove equality. Measure scan/hash/publish/flush latency and bytes on realistic synthetic corpora before setting a send-latency budget.

**[proposal]** Enforce per-file/checkpoint/store budgets before declaring completeness. Never silently truncate inventory, omit oversized LFS content or evict a live baseline. Mandatory capture failure retains the draft with a capability reason; choose limits from benchmarks.

**[proposal]** Retain all checkpoints supporting currently editable messages and all unresolved recovery operations. Proposed resolved-history retention: 30 days, configurable; quota pressure first expires resolved archived spans, visibly removing their file-rewind capability. Never automatically evict unresolved recovery. Session/worktree deletion must not cascade-delete recovery metadata/refs before the user has a recovery path. Mark expired capability in SQLite, flush, then remove refs; serialize maintenance with capture/apply. Run GC only in the private store with conservative grace; never prune the owner repo. Ref deletion is not secure erasure: packed objects, reflogs and backups may retain bytes.
