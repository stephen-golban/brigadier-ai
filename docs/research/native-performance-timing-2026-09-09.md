# Native performance timing — 2026-09-09

**Source-verified research, not a new native benchmark.** The existing rAF meter can hide sustained missed 60 Hz callbacks by relabelling their cadence as 30 Hz. Fix the measurement contract before comparing optimizations. rAF callback delivery does not prove that a compositor presented a new frame.

## The existing meter's blind spots

**Verified by source inspection** of `src/fps.ts` at the start of this task:

- `derivePeriod` chooses p10 when it is within 20% of p50; otherwise it chooses p50. It snaps the result to 120, 60, or 30 Hz. A sequence entirely composed of 33.333 ms intervals therefore becomes 30 Hz; `round(dt / budget) - 1` reports zero missed intervals, and `windowPasses` accepts it. At a separately confirmed 60 Hz target, the same sequence misses one opportunity per interval. This is an arithmetic counterexample, not a native replay.
- `windowPasses` does not require 60 Hz. `summarise` requires every window to pass, but every window is allowed to select its own slower budget. The reported minimum of 30 Hz is consequently not evidence that the display switched to 30 Hz.
- `sampleFrame` reads `performance.now()` after `feedStore` drains. Differences include changes in drain duration and callback scheduling delay; callback spacing can be shorter than a display period after a delayed callback. The comment that frames cannot arrive early is not a valid property of this sampling point.
- Every interval over 1,000 ms is discarded without checking document visibility. A foreground one-second stall must count as a failure, not be silently treated as a hidden window.

**Recommendation:** independently establish the display/target period, lock it for the capture, and report callback cadence separately. Preserve raw intervals, all missed opportunities, and invalid/interrupted runs. Use the rAF callback timestamp for rendering-opportunity spacing and separately time drain work; neither signal should be named a presentation timestamp. A burn interrupted by hiding the window must be marked invalid and repeated, rather than omit its inconvenient windows.

## What WKWebView timing means

**Documented/source-verified:** HTML defines rAF as callbacks executed during rendering updates. The timestamp is supplied to the callback; it is not an acknowledgement that the callback's future DOM work was displayed. WebKit's scheduler requests a display-refresh monitor, can fall back to a timer, and can reschedule instead of triggering an update. Its preferred frame rate incorporates display nominal frequency, throttling, animation requirements, and a setting to prefer updates near 60 FPS. Visually-idle and low-power state can alter throttling. These facts rule out inferring physical display frequency exclusively from a busy page's callbacks. [HTML animation frames](https://html.spec.whatwg.org/multipage/imagebitmap-and-animations.html#animation-frames), [WebKit scheduler](https://github.com/WebKit/WebKit/blob/main/Source/WebCore/page/RenderingUpdateScheduler.cpp), [WebKit Page](https://github.com/WebKit/WebKit/blob/main/Source/WebCore/page/Page.cpp).

**Limitation:** current upstream WebKit source establishes the mechanism, not the exact revision shipped by the host's macOS. Record the OS build, WKWebView user agent, screen, power state, window visibility and configured display mode with native results. Do not attribute an observed 30 Hz result to one particular throttle without a native probe.

## Verify the display independently

**Documented and confirmed in the installed Apple SDK headers:**

| Signal | Meaning | Limitation |
| --- | --- | --- |
| `CGDisplayCopyDisplayMode` + `CGDisplayModeGetRefreshRate` | Selected display mode's refresh rate | Mode metadata is not evidence of individual presented application frames. |
| `CVDisplayLinkGetNominalOutputVideoRefreshPeriod` | Device's ideal period as a rational `CVTime` | Can be indefinite; reject that result. |
| `CVDisplayLinkGetActualOutputVideoRefreshPeriod` | Period in seconds measured relative to the host timebase | Can return zero when stopped/unavailable; run the display link before querying. |

Use the display containing the measured window, not an assumed main monitor. Cross-check positive nominal and running actual periods; retain their provenance. A fixed 60 Hz mode gives a clear 16.6667 ms target. Variable-refresh metadata or zero values require further observation, not an automatic 60 Hz label. A CVDisplayLink observation still does not tell whether Brigadier's content was presented on a given refresh. [CoreGraphics display modes](https://developer.apple.com/documentation/coregraphics/cgdisplaymodegetrefreshrate(_:)), [nominal period](https://developer.apple.com/documentation/corevideo/cvdisplaylinkgetnominaloutputvideorefreshperiod(_:)), [actual period](https://developer.apple.com/documentation/corevideo/cvdisplaylinkgetactualoutputvideorefreshperiod(_:)). Header inspection: CommandLineTools SDK `CoreGraphics.framework/Headers/CGDirectDisplay.h` and `CoreVideo.framework/Headers/CVDisplayLink.h`.

## Startup measurement contract

**Verified in this repository:** `src/paint.ts` reports the buffered `first-contentful-paint` entry as `performance.timeOrigin + entry.startTime`; `src-tauri/src/commands.rs` subtracts a Rust main-entry wall-clock epoch. This excludes pre-main loading. The 4,228.675 ms observation is one main-to-FCP debug sample; it cannot establish exec-to-FCP p50. `src-tauri/tauri.conf.json` uses `http://localhost:1420` in development and bundled `../dist` assets for builds. Tauri documents this dev URL / frontend asset distinction. [Tauri build configuration](https://v2.tauri.app/reference/config/#buildconfig).

**Documented:** FCP is the first contentful rendering event. The current Paint Timing draft recommends the latest available pipeline timestamp, preferably submission to the OS; it does not promise photons or an application-specific “ready” milestone. The existing research recorded FCP support in this machine's WKWebView; recheck supported entry types and actual buffered entries in the measured binary, treating absence as unavailable. [Paint Timing draft](https://w3c.github.io/paint-timing/), [prior local probe](perceived-performance.md#53-paint-timing-is-usable).

**Documented:** `timeOrigin` refers to an estimated monotonic Unix epoch and can differ from `Date.now()`. Epoch subtraction across native/browser clocks is approximate, not guaranteed exact clock synchronization. Record `Date.now() - (performance.timeOrigin + performance.now())` near reporting and compare wall/monotonic elapsed time in the launcher; clock discontinuities invalidate the run. [High Resolution Time draft, time origin and clocks](https://www.w3.org/TR/hr-time-3/).

**Recommended reproducible protocol:** build first, then use a launcher that records epoch and monotonic timestamps immediately before spawning the executable. Keep the launcher timestamp outside the child and pair each launch with its own fresh data directory and one FCP record. Report this as **pre-spawn-to-FCP**, a conservative approximation of exec-to-FCP including launch-call overhead; retain main-to-FCP separately. Measure multiple independent launches, publish every sample, count missing FCP as failed samples, and compute the median only from a complete valid series. Label warm filesystem/WebKit cache conditions explicitly. Time debug/Vite and installed release independently, with Vite ready before debug samples, and no builds, HMR, inspector, screen capture or profiling during acceptance measurements. Profile in separate runs and then repeat the unchanged acceptance workload.

**Recommendation: justified to try.** Put the existing BrandMark and “Opening Brigadier…” status inside `index.html`'s initially empty `#root`, then let React replace it with the existing Launch flow. It communicates real progress already communicated by Launch, and removes JavaScript execution as a prerequisite for that message. FCP explicitly measures first rendered image/text, not application readiness. This improves the specified FCP milestone if native measurements confirm it; it must not be described as the workspace opening faster without a separate app-ready result. [Paint Timing definition](https://w3c.github.io/paint-timing/#first-contentful-paint).

**Documented scheduling:** module scripts fetch dependencies in parallel with HTML parsing and, absent `async`, execute after parsing. The implicit render-blocking script rule applies to parser-inserted classic scripts without async/defer, not ordinary module scripts. Thus HTML status has an opportunity to paint before the entry module executes. That opportunity is not guaranteed: the event loop can execute ready JavaScript before the next rendering opportunity. Do not add artificial timers or delay React startup solely to force a shell-only frame. The saved production HTML includes such an index stylesheet; adding inline critical status styles does **not** bypass that remaining stylesheet blocker. Inline status styles still ensure development's JS-injected CSS is unnecessary for a readable initial status. Keep the normal stylesheet loading intact for the first experiment; inspect the resulting built HTML and measure before considering broader CSS-loading changes that risk flashes of unstyled application content. [HTML stylesheet loading](https://html.spec.whatwg.org/multipage/links.html#link-type-stylesheet).

## Loaded rendering audit — 2026-09-10

**Read-only verification of the supplied native capture:** `/tmp/brigadier-perf-e2ce/release-unobstructed-burn.json` records ten sessions at 200 events/second each for 60 seconds, 62 reporting windows covering 63,501 ms, 1,384 sampled callback intervals, **2,499 missed 60 Hz opportunities**, worst interval/p95 105 ms, and no hidden-window interruption. Idle reports 60 callbacks and zero misses. DOM count grows from 1,299 idle to at most 1,562. This is a rendering failure with an independently fixed budget, not a refresh-inference artifact. Initial focus is false and final focus true; hidden remains false. Do not retroactively describe the whole run as continuously focused. Drain profiling is off, so its zero fields provide no CPU evidence.

**Most defensible source-level suspect: broad signal-driven React updates, not the old virtual Feed.** `App.runBurn` selects the newest replay session and mounts `ThreadView → Transcript`. A source search finds `Feed.tsx` used by tests only, not imported by the active application. Optimizing `Feed.buildFeed` or its virtualizer would not address this capture's selected transcript.

`feedStore.patch` always replaces the session and marks `stateDirty`; replay cycles the captured script, and the batcher's signal set includes session/turn lifecycle events. On a dirty drain, `rebuildState` replaces the whole snapshot, sessions record, order and approvals array. Both App and Transcript subscribe to that entire snapshot. This can run at drain cadence even though counters alone flush only every 500 ms. **Crucial limit:** row-only `notify()` with unchanged `getState()` does not by itself require an App render; React compares snapshots with `Object.is`. Count actual signal-driven rebuilds before asserting a render frequency. [React external-store snapshot contract](https://react.dev/reference/react/useSyncExternalStore).

**Verified downstream work and amplification candidates:**

- App filters/copies the session record when the snapshot changes, calls `conversationSessions` during JSX construction, and recreates attention maps, approval elements and inline callbacks. Sidebar, Dock and ThreadView are not memoized in the audited code. Sidebar repeats project/session filtering and sorting on each parent render; total existing projects/sessions therefore matter as well as ten newly generated sessions.
- `useAttention` watches the viewed session's `lastEventSeq`. When that sequence advances it calls `markSessionRead`, which synchronously reads/parses localStorage, writes the updated map, and dispatches an event whose handler parses the map again and calls `setReads`. This can add persistence work and an App update to each acknowledgement. Whether the actual capture selected a viewed-session target for this hook needs runtime counters; source alone does not establish its share of the stall.
- Transcript reads the entire store but only uses its selected session's busy/stop/project fields and approval membership. It also executes a localStorage scroll-state initializer IIFE on every render despite placing the result inside `useRef`; JavaScript evaluates that argument before calling the hook. Approval matching scans all projected work nodes before virtualizing the visible rows. Repeated unrelated store updates can therefore do work even with bounded DOM.
- `useConversationHistory` always merges/sorts the history and publishes a fresh items array after an updates response, including empty update pages. It also requests chat turns whenever merged items exist. Unchanged data can invalidate `projectThread`, message conversion and transcript rendering. An equality-preserving no-op path for empty/identical pages is defensible; it must preserve turn changes, deletion/revision handling and history paging semantics.
- `appendRing` concatenates and slices both project and session rings per batch. This is a separate allocation candidate, but changing it before measuring drain time would be guesswork. React commit/layout work may happen outside the existing synchronous drain measurement; a short drain does not clear the rendering path.

**Recommended diagnostic, then smallest justified fix:** record per-second counts of state rebuilds by cause, App/Sidebar/Transcript commits, history responses that contain no changes, and read-state persistence writes. Buffer diagnostics and export after the run. If profiling confirms the broad update path, subscribe Transcript to a cached selection of only its necessary session/approval fields; make Sidebar's inputs and callbacks stable and memoize the subtree. Keep acknowledgement state immediate in memory and consider coalescing persistence with explicit flush on session change/teardown. Fix the repeated scroll read independently with true once-per-session initialization. Preserve all real signals, approvals, counters and the full replay rate; do not achieve the number by hiding updates.

React's default `memo` comparison checks each prop by `Object.is`; wrapping Sidebar alone while passing new records/elements/functions will not skip those updates. A custom comparator must not ignore callbacks or fields needed for behavior. `useSyncExternalStore` snapshot objects must be cached and immutable, and wrapping external mutations in `startTransition` does not make them nonblocking. [React memo](https://react.dev/reference/react/memo), [external-store caveats](https://react.dev/reference/react/useSyncExternalStore).

For component CPU attribution, `<Profiler>` reports subtree render durations and commit identity. Ordinary production React disables profiling; use a separately identified profiling-enabled production build or a diagnostic development run, never infer a missing callback means zero work. `actualDuration` is React render time, not a browser paint/presentation measurement. Return to the ordinary acceptance binary afterward. [React Profiler](https://react.dev/reference/react/Profiler).
