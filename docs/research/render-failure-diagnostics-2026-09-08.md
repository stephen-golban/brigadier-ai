# React render failure containment and local diagnostics

Fetched 2026-09-08. Scope: prevent a React render exception from leaving a blank window, and retain bounded diagnostics locally. No external reporting.

**[asserted] Recommendation:** add one outer error boundary above `ThemeProvider`, record React errors through `createRoot` callbacks, and send a small diagnostic record through one Tauri command to an app-owned rotating file. This is containment and instrumentation; it does not establish the cause of the reported blank window.

**2026-09-08 follow-up:** the parent task reproduced the native failure after diagnostics were installed. The logged exception maps to the message renderer's unchecked Brigadier metadata access; the exact assistant-ui source path below explains how an ordinary running placeholder reaches it. The earlier containment findings remain useful, but a renderer guard is now the targeted fix.

## Evidence and API contract

- **[source]** `src/main.tsx:16` creates the only React root without options or an error boundary. `rg` over `src/` found no error-boundary or global-rejection registration. Installed `react` and `react-dom` are both **19.2.8** (`node_modules/*/package.json`); `node_modules/@types/react-dom/client.d.ts:37` declares the root callbacks below.
- **[documented]** An unhandled render error removes the React UI. A class extending `Component` with `static getDerivedStateFromError` can switch to a fallback. Boundaries catch descendants, not themselves, and exclude ordinary event handlers and asynchronous callbacks. `componentDidCatch` is optional for side effects. [React Component reference](https://react.dev/reference/react/Component#catching-rendering-errors-with-an-error-boundary).
- **[documented]** `createRoot(container, options)` accepts `onCaughtError(error, errorInfo)`, `onUncaughtError(error, errorInfo)`, and `onRecoverableError(error, errorInfo)`. `errorInfo` includes `componentStack`; recoverable errors may carry `cause`. These callbacks report errors; they do not specify fallback rendering. Custom callbacks replace the corresponding default reporting path, so preserve useful console output deliberately. `root.render()` is not synchronous with surrounding JavaScript; wrapping only that call in `try/catch` is not the solution. [React createRoot reference](https://react.dev/reference/react-dom/client/createRoot).
- **[documented]** Since React 19, render errors are not rethrown as in earlier versions. Defaults route uncaught errors to `window.reportError` and caught errors to `console.error`. Global listeners alone therefore do not cover boundary-caught failures. [React 19 upgrade guide](https://react.dev/blog/2024/04/25/react-19-upgrade-guide#errors-in-render-are-not-re-thrown).
- **[documented]** Browser error reporting uses `ErrorEvent`; unhandled promise reporting uses `PromiseRejectionEvent` and its `reason`. Register supplemental `error` and `unhandledrejection` listeners before mounting. **[asserted]** Keep their default console behavior and deduplicate overlapping reports. [HTML Standard: runtime script errors](https://html.spec.whatwg.org/multipage/webappapis.html#runtime-script-errors), [unhandled promise rejections](https://html.spec.whatwg.org/multipage/webappapis.html#unhandled-promise-rejections).

## Minimal implementation shape

1. **[asserted]** Put the boundary outside `ThemeProvider`, `Launch`, and `WindowChrome`. Its fallback should use plain HTML controls and independent styling, avoiding the providers and rich message renderer that may have failed. Offer a user-triggered reload; do not automatically resend a message or restart a session. Explain only the rendering failure and whether diagnostics were saved.
2. **[asserted]** Report caught errors in one place: root `onCaughtError`, or boundary `componentDidCatch`, not both. Using root hooks for all three React categories keeps classification consistent. Make every reporter nonthrowing, including unknown-value formatting and rejected logging promises. A logger failure must not create another unhandled rejection.
3. **[asserted]** Include category, timestamp, error name/message/stack, component stack, and build identity. Avoid whole messages, tool results, session dumps, arbitrary object serialization, and environment variables. Error strings can themselves contain content, so bounded diagnostics are not a claim of automatic secret redaction.
4. **[asserted]** Enforce limits on both sides: for example, 4 KiB message, 16 KiB JavaScript stack, 16 KiB component stack, plus a maximum encoded-record size. Rust limits must be UTF-8 safe. Bound in-flight reports and suppress repeated signatures to prevent error loops flooding IPC.
5. **[asserted]** Use one fixed filename such as `frontend-errors.ndjson` under the resolved app data directory, never a caller-supplied path. Serialize writers with a mutex; before append, rotate to one previous file when the next record would exceed **1 MiB**. Reject any record exceeding the file cap. This proposal bounds retained data to **2 MiB** across current and previous files. Keep the original file if rotation fails and return an error rather than silently truncating it.

## Tauri and disk interfaces

- **[documented]** Import `invoke` from `@tauri-apps/api/core`; register a `#[tauri::command]` using `generate_handler!`. Inputs deserialize through Serde, default top-level argument keys are camelCase, and a command returning `Result` resolves/rejects the JavaScript promise. Async commands execute in an async task; ordinary synchronous commands execute on the main thread. [Calling Rust](https://v2.tauri.app/develop/calling-rust/).
- **[source]** Command names belong in `src/bridge.ts` under its documented transport convention. `src-tauri/src/lib.rs:133` has the central command registration. The project requires crate-unique `pub(crate)` commands (`docs/STATUS.md`, landmines). The logger should not depend on `AppState::ready`, because launch failure is itself worth diagnosing.
- **[documented]** `app.path().app_local_data_dir()` resolves the app's local-data directory using its bundle identifier. On macOS, the base is `~/Library/Application Support`. `app_log_dir()` instead uses `~/Library/Logs/<identifier>`. **[source]** This app already uses `app_local_data_dir()` at `src-tauri/src/lib.rs:249`. [Tauri PathResolver](https://docs.rs/tauri/latest/tauri/path/struct.PathResolver.html#method.app_local_data_dir).
- **[documented]** Rust `OpenOptions` supports create/append; append does not remove the need to coordinate multiple writers. **[asserted]** Hold the same mutex across size check, rotation, and `write_all`, and execute blocking filesystem operations via `spawn_blocking` from the async command. [Rust OpenOptions](https://doc.rust-lang.org/std/fs/struct.OpenOptions.html#method.append), [Tokio spawn_blocking](https://docs.rs/tokio/latest/tokio/task/fn.spawn_blocking.html).
- **[documented]** Tauri's logging plugin supports frontend logs, file targets, configurable maximum size and rotation. **[source]** It is not currently a dependency; the app already initializes `tracing_subscriber` at `src-tauri/src/lib.rs:388`. **[asserted]** A dedicated command avoids introducing a second general logging system for this small requirement. Do not choose the documented `KeepAll` example when retention must be bounded. [Tauri logging plugin](https://v2.tauri.app/plugin/logging/).

## Verification and limits

**[asserted] Required checks:** inject a descendant render exception and confirm a visible fallback plus one persisted React record with component stack; reject the logging command and confirm the fallback still works with no reporting loop; exercise non-Error and Unicode values; run concurrent writes and enough records to force rotation, verifying parseable NDJSON and byte limits. Confirm the packaged Tauri app writes the file through actual IPC. A browser mock alone cannot prove disk persistence.

**[unverified at initial research]** No render exception, recovery behavior, or filesystem command was executed in the initial research task; no application code was changed by this researcher. Parent task reported that normal live messages/list tools passed and that the user manually quit after the blank screen. The later evidence below supersedes the original absence of a reproduction. A boundary cannot repair a dead/hung WebView, native crash, failed JavaScript module load before handler registration, or an exception inside its own fallback. Local persistence is best effort while IPC and the native process remain alive; an acknowledged write is not a power-loss durability guarantee.

## Reproduced cause: assistant-ui's optimistic message

- **[measured: read-only inspection]** `/Users/stephen/Library/Application Support/ai.brigadier.app/frontend-errors.ndjson:1` contains `undefined is not an object (evaluating 'z.type')`, timestamp `1788899497048`, with top frame `children@tauri://localhost/assets/App-CeUeFID2.js:22:1237` and `ThreadPrimitive.Messages` in the component stack. The parent task ran the native reproduction; this researcher read the persisted record.
- **[source]** In the matching `dist/assets/App-CeUeFID2.js:22`, `z` is assigned `R.metadata.custom.brigadier` immediately before `z.type` in the message CSS-class expression. This matches the pre-fix `src/components/ThreadView.tsx:359-365`: the renderer casts custom metadata to `ThreadRow` and immediately dereferences `row.type`. The cast performs no runtime check.
- **[source]** Installed versions are `@assistant-ui/react` **0.15.18** and its runtime `@assistant-ui/core` **0.3.17**, read from their package manifests. The React package re-exports these runtime primitives from core. At `node_modules/@assistant-ui/core/src/runtimes/external-store/external-store-thread-runtime-core.ts:74-78`, `hasUpcomingMessage` returns true when the effective running state is true and the final external message is not an assistant. **An empty array also satisfies this condition.**
- **[source]** At the same runtime file's lines **447-468**, that condition appends a generated assistant message with empty content, `metadata.isOptimistic = true`, and running status. It is inserted after conversion of external messages, so the app's `convertMessage` does not add Brigadier metadata to it. The repository then becomes the published message array. `node_modules/@assistant-ui/core/src/runtime/utils/thread-message-like.ts:219` supplies `metadata.custom = {}` when custom metadata is absent; therefore the synthetic message's `metadata.custom.brigadier` is undefined. The upstream implementation matches the installed code. [assistant-ui runtime source](https://github.com/assistant-ui/assistant-ui/blob/main/packages/core/src/runtimes/external-store/external-store-thread-runtime-core.ts).
- **[source]** `node_modules/@assistant-ui/core/src/react/primitives/thread/ThreadMessages.tsx:241-263` iterates the runtime's entire message array and calls the supplied renderer for each message. It does not exclude optimistic messages. Brigadier supplies `isRunning: busy` at pre-fix `src/components/ThreadView.tsx:292`; metadata is only attached to its own projected rows at line **285**.
- **[documented]** The official external-store guide explicitly says that `isRunning` displays an optimistic assistant message. It also documents that runtime-visible message paths may include optimistic leaves which are absent from canonical persisted history. This is supported library behavior, not evidence of a corrupted stored message. [ExternalStoreRuntime guide](https://www.assistant-ui.com/docs/runtimes/custom/external-store#api-reference).

**[asserted: fix derived from source and native record]** Before accessing `row.type`, handle a message with absent Brigadier row metadata. A small pending-response placeholder is appropriate when `metadata.isOptimistic` is true; the application may also return no row when it already renders a waiting indicator. Do not manufacture a persisted `ThreadRow`, disable `isRunning`, or depend on `isLoading` suppressing this callback. Preserve rendering of supplied user, work, and assistant rows.

**[asserted: regression requirements]** Use the actual installed `useExternalStoreRuntime` and `ThreadPrimitive.Messages`: test busy with zero saved rows, busy with a trailing user row, and transition to a real assistant/work row. Verify visible waiting state and absence of a render exception, then verify the real row replaces the synthetic one. A mock that merely maps the provided external `messages` omits the library-created message and cannot detect this bug. Parent task owns implementation and regression execution; this research update does not claim those tests passed.
