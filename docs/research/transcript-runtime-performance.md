## Burn delivery visibility audit, 2026-09-11

The [quiet-session capture](/tmp/brigadier-release-20260911/burn-quiet-session.json) is uninterrupted but fails both delivery and rendering. Its durable stream contains 108,044 terse rows; Channel ingestion contains 107,968, exactly 76 fewer. Backend counters report 52 dropped rows for session 0, 24 for session 1, and zero for the other eight. Rendering independently reports ten missed frame opportunities; fixing delivery does not make that capture pass.

The source exposes an initial visibility race:

1. [Rust burn setup](../../src-tauri/src/burn.rs#L58) creates a new project and sequentially starts all sessions before the invoke resolves. It does not make the project visible first.
2. [App.runBurn](../../src/App.tsx#L1025) waits for that invoke, then refreshes projects and selects the replay project/session. Early replay rows therefore arrive before this explicit selection.
3. [The visibility effect](../../src/App.tsx#L500) publishes selected, projectless, and worker project IDs. [Batcher.push](../../crates/supervisor/src/batcher.rs#L167) drops invisible rows immediately, while retaining signals and counters. A later selection or history read cannot retroactively deliver those rows through Channel.
4. Unknown-project signals also trigger a delayed project refresh, after which selection fallback can choose the new non-projectless project. This explains why loss can stop before runBurn returns. Inference: at 200 fixture events/s and eight terse rows per nine-event cycle, 52 and 24 dropped rows imply a common visibility boundary near 465 ms (session starts 172 and 329 ms respectively). The capture lacks visibility transition timestamps, so this arithmetic corroborates the race rather than proving the exact interleaving.

Recommended minimal robust invariant: acquire a scoped visibility pin for **only the new burn project**, after creation and before the first `start_session`. Batcher visibility becomes the normal UI set **or** an active pin; `set_visible_projects` continues replacing only the UI set. Hold the pin through replay kills and exit-event enqueue, releasing it on success and every error path. A per-project reference count/RAII guard permits overlapping owners without stale restoration. Only the existing debug/burn harness acquires it. This leaves the real driver, store, batching, Channel, frontend ingestion, selected transcript mount, capture start, rates, duration and gate unchanged. It adds delivery work previously lost; it does not prewarm transcript rendering.

A single backend `set_visible_projects([burn_id])` is insufficient: a subsequent App effect containing projectless IDs can overwrite it. Suppressing that effect requires coordinating already-issued invokes and restoring the latest UI set; splitting prepare/start requires an explicit frontend visibility acknowledgement. Both are wider coordination changes than a scoped project pin. Do not replay missing rows from history, reset counters, delay capture, or loosen delivery assertions.

Channel readiness is a separate precondition: [mount subscribes without awaiting](../../src/App.tsx#L325), although automatic burn currently waits 20 seconds. For a strict first-event guarantee, await the existing subscription's successful acknowledgement before starting producers; do not replace the channel for the benchmark. Verify the pin survives a competing visibility replacement and releases correctly, then rerun the unchanged native delivery/rendering gate.

## Direct ExternalThread audit: defer migration

Recommendation: **keep the current writable runtime for this fix**. The supported direct resource removes the legacy runtime bridge, but it changes behavior that a small provider substitution cannot preserve. A reported 7 ms initial runtime hierarchy is a profiling observation, not evidence of the direct resource's savings.

The installed public imports and provider composition are:

```tsx
import {
  AuiProvider, AuiConfig, ExternalThread, fromThreadMessageLike,
  type ThreadMessage,
} from "@assistant-ui/react";

// fullMessages must already be normalized and identity-cached.
// onNew/onCancel below are resource callbacks, not awaitable runtime actions.
const config = AuiConfig({
  thread: ExternalThread({
    messages: fullMessages satisfies readonly ThreadMessage[],
    isRunning: busy,
    isLoading: !loaded,
    onNew,
    onCancel,
  }),
});
return <AuiProvider config={config}>{children}</AuiProvider>;
```

This is composition syntax, **not an equivalent replacement implementation**. `ExternalThread` is a resource factory, not a JSX component. `AuiConfig` may be created each render; its identity does not control resource lifetime. A nested provider must explicitly specify `extends={aui}` or `extends={null}`. Installed provider contract (installed `node_modules/@assistant-ui/store/src/AuiProvider.tsx:29`), [official runtime API](https://www.assistant-ui.com/docs/api-reference/external-store/runtime).

Parity requirements and hazards:

- Normalize each `ThreadMessageLike` with the exported `fromThreadMessageLike(like, fallbackId, fallbackStatus)`; a type cast loses content normalization, metadata defaults, attachments and IDs. For this app's text/empty-content inputs, legacy fallback status is running only for the final message while busy, otherwise complete with reason `unknown`; explicit message status wins. Cache by input identity and effective fallback status so busy changes preserve earlier messages. Full tool-call inputs additionally require the library's pending/interrupt status rules. Installed conversion and cache (installed `node_modules/@assistant-ui/core/src/runtimes/external-store/external-store-thread-runtime-core.ts:359`).
- Direct composer/send and cancel callbacks return void; the resource invokes them without awaiting their promises. Legacy append awaits `onNew`. Simply reusing the existing async bridge callbacks therefore changes error propagation and send completion semantics. Direct composer clears its draft before callback dispatch. It also does not insert an optimistic user message: the host must publish one if desired. Do not add a new optimistic insert to this app incidentally. Direct send (installed `node_modules/@assistant-ui/core/src/store/clients/external-thread.ts:684`), legacy append (installed `node_modules/@assistant-ui/core/src/runtimes/external-store/external-store-thread-runtime-core.ts:639`).
- Legacy runtime adds an empty optimistic assistant while busy without a trailing assistant; direct ExternalThread exposes exactly the supplied messages. That affects message-presence/initial-scroll state even though Brigadier renders saved rows separately. Direct resource also omits legacy runStart/runEnd notifications. The current viewport explicitly disables run-start scrolling, but initial empty→busy behavior still needs parity testing. Legacy placeholder (installed `node_modules/@assistant-ui/core/src/runtimes/external-store/external-store-thread-runtime-core.ts:447`), [app viewport](../../src/components/assistant-ui/elements/thread.tsx#L29).
- ExternalThread supplies single-thread-list and composer scopes, so existing `ThreadPrimitive` viewport and `useAui().composer()` remain structurally supported. It does not supply the legacy AssistantRuntime context. Keep the read-only branch, including its rejected send/edit behavior, unchanged. Scope installation (installed `node_modules/@assistant-ui/core/src/store/clients/external-thread.ts:1173`).

A future migration needs actual-runtime tests for normalization/identity, successful and rejected sends, cancellation, optimistic empty/user tails, session switching and viewport following before a cold native comparison. That scope is wider than the current local optimization.

## Viewport containment and initial measurements

Source-only conclusion: **no duplicated synchronous size read is caused by the two viewport providers**. The outer provider (installed `node_modules/@assistant-ui/react/src/legacy-runtime/AssistantRuntimeProvider.tsx:57`) creates a store; provider nesting (installed `node_modules/@assistant-ui/react/src/context/providers/ThreadViewportProvider.tsx:19`) forwards scroll requests and bottom-state changes through passive effects. Neither attaches a measurement ref. The inner Viewport (installed `node_modules/@assistant-ui/react/src/primitives/thread/ThreadViewport.tsx:90`) reads `clientHeight`; the Footer (installed `node_modules/@assistant-ui/react/src/primitives/thread/ThreadViewportFooter.tsx:53`) reads computed margin and `offsetHeight`. Each useSizeHandle (installed `node_modules/@assistant-ui/react/src/utils/hooks/useSizeHandle.ts:19`) installs ResizeObserver and measures immediately at ref attachment. These reads can flush dirty layout, but their elapsed cost is not established by a combined commit span. Removing the outer provider would not remove them.

Containment is suitable only as a reversible A/B hypothesis. Prefer testing `.aui-viewport { contain: layout; }` alone first, rather than both viewport and thread: this isolates the narrower existing scroll region and avoids conflating two boundaries. Its [existing markup](../../src/components/assistant-ui/elements/thread.tsx#L27) uses flex allocation, `min-height:0`, and `overflow-y:auto`. Virtual rows already have a local relatively positioned spacer; message actions have positioned message ancestors. These are supporting structural facts, **not proof of unchanged computed geometry**.

Required invariant: for the same window, shell and content, containment must preserve viewport/content width, allocated height, scroll range, measured row offsets, sticky footer position, restoration and user-controlled following. Layout containment does not add size or paint containment, so it neither guarantees independent intrinsic sizing nor skips initial content work. It does establish a containing block for absolute/fixed descendants and a stacking context. `style` adds counter/quote scoping; it is not CSS selector or inheritance isolation. Therefore `layout style` is a second experiment only after checking ordered Markdown lists/quotes. Avoid `strict`, `content`, `size`, `paint` and `content-visibility` substitutions. [CSS containment specification](https://www.w3.org/TR/css-contain-2/#containment-layout), [style containment](https://www.w3.org/TR/css-contain-2/#containment-style).

Sticky positioning remains tied to the nearest scrollport, so keeping the same overflow element is necessary; containing-block and stacking changes still need visual checking. [CSS sticky positioning](https://www.w3.org/TR/css-position-3/#sticky-pos). Test short/long and virtualized histories, resized split panes, expanded work/approval cards, restored mid-history position, ongoing following, Jump to latest, and popovers/tooltips/dialogs while scrolled. The installed UI wrappers use portals, but only overlay DOM mounted **outside** the contained element escapes its containment; check the actual portal container. `.aui-thread` is broader and creates the same stacking/fixed-position hazards, so it is not inherently safer.

Compare unchanged cold full-feed captures and initial layout traces; retain containment only with measured improvement and the geometry/interaction invariants intact. Do not move either initial measurement to a later frame to improve the capture. The first two seconds remain part of acceptance, and no runtime migration is proposed.

## Actual-history timestamp formatting in a Worker

**Recommendation: a bounded candidate, with locale parity and failure handling required.** [useConversationHistory](../../src/hooks/useConversationHistory.ts#L50) already receives a complete page, merges it, awaits `chatTurns`, checks `live`, and then publishes. Start label preparation from that real response concurrently with the existing turns request; await both before the existing publication. Keep page contents, cursors, feed notifications and polling unchanged. Send only actual required timestamps and formatting context, not chat bodies. No Worker creation, formatter construction or synthetic formatting at module import/app startup. A Worker may remove main-thread formatting while adding startup/message latency; publication waits for the slower operation, so this is not a demonstrated latency win or permission to relax delivery/freshness acceptance.

The exact supported constructor is:

```ts
new Worker(new URL('./timestamp.worker.ts', import.meta.url), { type: 'module' })
```

Keep `new URL` directly inside `new Worker`, with a literal path and static options. [Official Vite Worker syntax](https://vite.dev/guide/features.html#web-workers) and installed Vite 7.3.6 transformation (installed `node_modules/vite/dist/node/chunks/config.js:27670`) support this and emit a production worker asset. [CodeEditor](../../src/components/CodeEditor.tsx#L4) already uses Vite `?worker` constructors for Monaco; that is packaging precedent, not proof of the new module worker's production WKWebView loading. [Tauri config](../../src-tauri/tauri.conf.json#L31) has `csp:null`, with no dev override; no CSP change is needed for this candidate. [Tauri CSP documentation](https://v2.tauri.app/security/csp/) says protection is enabled only when configured; the installed schema (installed `node_modules/@tauri-apps/cli/config.schema.json:1175`) describes production/dev inheritance. Keep the worker pure: no Tauri API, React, DOM or workspaceApi imports.

**Formatting contract:** current [MessageTimestamp/MessageTime](../../src/components/MessageTimestamp.tsx#L6) formats with locale `undefined`, local timezone, and existing options. `navigator.language` is only an invalidation key; substituting it as an explicit formatting locale is not automatically equivalent. ECMA-402 derives missing locale/timezone from host defaults; matching Window/Worker defaults in the same WebKit environment is a reasonable expectation, not a cross-realm equality guarantee established by that specification. Preserve identical arguments in worker and fallback; pass explicit locale/timezone when already part of the application's formatting contract, consistently to both. Do not construct `Intl.DateTimeFormat().resolvedOptions()` on the main thread merely to discover the zone: that can reintroduce the measured cold cost. [DefaultLocale](https://tc39.es/ecma402/#sec-defaultlocale), [DateTimeFormat initialization](https://tc39.es/ecma402/#sec-initializedatetimeformat).

Return time and short-date labels separately with their timestamp/context identity. Compute `Today` at render using the current local date, preserving midnight behavior and `<time dateTime>`. Reject prepared labels when language or local timestamp day/time/offset no longer matches; do not use UTC-minute-only keys. Warm-cache hits must be synchronous and bounded. Missing, stale or failed preparation uses the existing synchronous formatter, including for live timestamps absent from the prepared page. Check historical dates as well as Today so date formatting does not become the next cold Intl call.

**Minimal lifecycle:** lazily own one Worker per history-effect lifetime, reuse it for that lifetime's real requests, and terminate on effect cleanup. Settle pending requests on cleanup as well—`terminate()` alone does not settle application Promises. Use request IDs, a single-settlement guard and the existing `live` check after all awaits; ignore late replies and stale locale/session generations. Handle absent Worker, constructor/postMessage throws, worker `error`/`messageerror`, explicit formatting-error replies and invalid response shape. Resolve these as “no prepared labels,” not a history load error. A finite failure watchdog prevents a silently stalled worker blocking the page; clear it on every settlement and terminate/disable the failed worker for that effect. The watchdog is failure recovery, not a normal scheduling delay. Cleanup/StrictMode must leave no pending request or old-worker listener. [HTML Worker messaging and termination](https://html.spec.whatwg.org/multipage/workers.html#dedicated-workers-and-the-worker-interface).

Focused checks only: worker/fallback label parity across locale, midnight and DST cases; full-page publication waits for both existing turns and preparation while preserving contents; unsupported/error/timeout preparation still publishes; cleanup/session switch suppresses old replies; and cache hits do no Worker work. One relevant production WebKit check must establish worker loading and include worker startup through complete history publication in the existing capture.
