## 4. What a second vendor found that I had got wrong

Two `codex` passes, read-only. Both found real defects. I verified every citation in source before
acting on it — which is the reason to keep using it, and the reason not to trust it blind.

**The one that would have shipped a loop that hangs.** My wall policy sent Bash classified `Mutate`
to *allow* and `Unknown` to *ask*. But **`cargo test` and `npm test` classify `Unknown`** —
`crates/core/src/wall/bash.rs:487`, whose own doc comment says *"`npm test` must not come back
`Mutate`"*, and `:817` asserts it. **[source]** Every worker would have parked on its first
verification command. The policy was rewritten as an **allowlist**, whose failure mode is a parked
work order rather than a silent escape.

**The escape check missed the escape it was named for.** I cited
`GIT_REMOTE_MUTATE_SUBCOMMANDS` for `git push`; that constant holds the subcommands of `git remote`
and does not contain `push` (`tables.rs:175` vs `:208`). **[source]**

**Two holes in the wall I had just shipped**, both confirmed live by the worker before fixing:
`GIT_WORK_TREE=/tmp/victim git reset --hard` returned **allow** (an assignment is peeled off before
the guard sees it), and `cargo test --target-dir=/tmp/out` returned **allow** (the word begins `-`,
not `/`).

**A one-line SQL defect with a real consequence.** `phases.base_sha` used
`COALESCE(excluded, stored)`, so any later non-null value **overwrote the phase's base** — precisely
the bug the column was added to prevent. The test meant to pin it passed either way.

**A finding I verified, did not fix, and am telling you about instead.**
`crates/core/src/claude/adapter.rs:1286` files a turn's text under whichever turn is *closing*, and
`:1050-1070`'s own comment records that attribution is approximate across a pre-emption. A
continuation's text can therefore be returned as another turn's final answer, **silently**. It is
**not reachable by this loop** — a pre-emption needs a second `SendTurn` and every child the loop
spawns is one turn and disposable — but that safety rests on a rule, not on the code.
`docs/plans/w1b-loop-order.md` §7.8, with the cheap fix.

## 5. Three things the workers found that you should decide

**5.1 Every `work_order` intent row is unsweepable, by construction.** `sweep_settled` deletes only
`done`/`not_done`, and the 2026-09-04 narrowing holds every work order at `unknown`. It is the only
kind with that property. On `intent-records.md` §6's own **[asserted]** estimates that is ~48
rows/hour, ~**84 MB/year** of continuous running against a 200 MB warning threshold. Sharper: §6
justifies never sweeping `unknown` rows with *"they are few"* — and the narrowing, written after §6,
made the most frequent kind land there unconditionally. **The premise the retention rule rests on is
now false.** The worker changed nothing, correctly: overriding a documented rule with a stated
safety reason is your call. The remedy is one line and reuses the discrimination now built — sweep
settled-`unknown` rows whose outcome is `acked` or `operator`, leaving `reconciled` and `open`
immortal as intended.

**5.2 A dead button, found and fixed, but the class is worth noting.** The plan card's *mark done /
mark not done* wrote through `intent_close`, whose `state = 'open'` guard rejects exactly the
`unknown` rows the button exists for. It did nothing, and returned success. Fixed with a separate
operator path; `intent-records.md` §10.4 still claims it was *"a thin wrapper away"*, which is the
false line that produced the defect.

**5.3 `plans.status` has no transition beyond approval.** So `stop_run` records `abandoned` for the
current launch only — after a restart the plan reads `approved` again — and `done` is derived from
*every phase green* rather than stored. `RunView.status` is partly a computed field.

## 8. One measurement that changes how the gate has to work

`docs/research/orchestration-loop.md` §6.2 left the gate's `PATH` open and said outright it must not
be guessed at. I measured it; full method and caveats in `docs/research/gate-environment.md`.

**A Finder-launched macOS app gets `PATH=/usr/bin:/bin:/usr/sbin:/sbin`. In it `cargo` is MISSING
and `npm` is MISSING**; `git` is present. **[measured]** So a brigadier you double-click would run
`cargo test` as a verify command and get **exit 127** — which without a `command_not_found` slug
reads as *"the code is broken"* rather than *"this machine's PATH lacks the tool the plan named"*.

The trap in measuring it: `open(1)` from a shell **propagates the caller's environment**, so the
obvious method measures your terminal, not the launch. The number above came from making Finder
itself the launcher.

`$SHELL -l -c` does not fix it (a login-but-non-interactive zsh skips `.zshrc`). `$SHELL -l -i -c`
finds `npm` but **still not `cargo`**, and took between **5 and 13 seconds** — an interactive shell
with no tty is a hang risk, not merely slow. `~/.cargo/bin` is on no PATH on this machine at all,
including the one your own subagents were given, which cost the first hour of this run until I found
it.

This also narrows a landmine in your run plan, which says that prefix is needed *"from a
non-interactive shell"*. Too narrow: it is needed from an interactive login shell too.

  worker that parks on an approval, or a restart mid-flight.
- **The rung-1 fixer has never fixed anything live.** The red-gate ladder is covered by tests only.
- **The reconciler settles nothing.** It publishes the conservative outcome; the per-kind
  postcondition evaluator of `intent-records.md` §4.3 is deferred and its rustdoc says so.
- **Four of the five live sessions ended `failed` with signal 143.** That is the loop killing its
  disposable children and is expected — but the session rows read `failed` for children that did
  their job, which will look wrong in the sidebar.
- **The worker wall is not a sandbox and does not claim to be.** Its rustdoc names a real blind
  spot: the path guard reads a command's arguments, not its redirection targets, so
  `cat </etc/passwd` reads outside the worktree without asking.
- The `codex` review of the loop's own final diff was **not** run — the two passes covered the
  decisions and the store/core diff, not `crates/supervisor/src/loop_/`.
